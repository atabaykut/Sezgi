# Security Policy

Sezgi reads application source code and, in the opt-in live mode, forwards requests from AI agents to a test copy of an application (or, as an experimental feature, to its real data after it is opened in a terminal) on behalf of a human. Security reports are taken seriously.

## Supported versions

Only the latest released version receives security fixes. 0.1 is experimental and has not had an independent security audit; live mode writes to declared test copies and, as an experimental feature, to real data opened in a terminal, with every real-data step confirmed with a human password checked against a system anchor that only an administrator can set up. An agent or a script with shell access under the same user account cannot pass that check without the password; it is not a defence against a program that learns the password, runs as administrator or calls the application directly with the stored session (see *Threat model*).

## Reporting a vulnerability

Please do **not** open a public issue. Report privately through GitHub: **Security → Report a vulnerability** on the repository (private vulnerability reporting). Include a description, reproduction steps and the affected version. You will receive an acknowledgement within 72 hours.

## Threat model

Sezgi is designed to be run on **untrusted repositories and untrusted files**. In scope:

- Reading outside the repository (symlinks, `package.json` paths, git refs, workspace discovery). Sezgi does not follow symlinked files, keeps schema paths inside the repository and stops workspace and front-end discovery at the git root. C# projects referenced with `<ProjectReference>` outside the app folder are read only when they stay inside the repository or solution folder.
- Resource exhaustion (source files are skipped above 4 MiB and reported, maps above 64 MiB are not read; MCP lines and Ayna requests are size-limited).
- Prompt injection through code-derived text (summaries, rule texts) and through names read from shipped files or pages (WebMCP tool names a page declares are untrusted: cleaned, shortened and never called). Invisible and direction-changing characters are replaced (Unicode categories Cc, Cf including Tag characters, Co, Zl/Zp, variation selectors, invisible fillers), length is limited and the MCP instructions tell the agent this text is data.
- Crashes on hostile input: alias, inheritance, zod and wrapper chains (and Java constants, class hierarchies and Spring Data repository chains) are followed with cycle detection and depth limits; syntax trees are walked without recursion (Ruby DSL blocks, arguments and nested classes stop at a fixed depth). PHP is never executed: Laravel route files, `require` targets and loader helpers are evaluated statically, only paths that resolve to files already read inside the application are followed, with cycle detection and step limits. The Go adapter follows route-setup code by reading it, never by running it, with a call-depth limit, a recursion guard and a step budget. Files read without source code (`sezgi kesfet`: Windows executables, ELF files, Android APKs, SQLite databases, Electron `app.asar` packages) are parsed by bounds-checked readers, never loaded, opened by a database engine or executed; an `app.asar` entry whose path is not safe is skipped.
- Writes: `sezgi init` writes only into its output folder and never through symlinks: `kapilar.json`, `benlik.json`, `benlik-evidence.json`, `openapi.json`, `kanit.json`, `graf.json`, `web-baglari.json` (when a front end is found), `benlik-keys.json` (when signed) and a `.gitignore` when the folder is the default `<app>/.sezgi`. `sezgi kesfet` writes `kaynaksiz.json` and the same map, evidence and card files into its output folder; the JavaScript of an Electron package is extracted to a temporary folder for reading and deleted afterwards. `sezgi gozlem al`, `sezgi gozlem senaryo` and every request live mode sends write `gozlem.json` into the map folder (request shapes only, see "Observation" below). None of them modifies application files. The switchboard writes into the user's configuration directory, owner-only (on Unix the folder `0700`, files `0600`): `santral.json` (registered apps and their local paths), `santral-baglar.json` (cross-links), `santral-varliklar.json` (entity mappings, schema level, no record values) and `santral-planlar/<id>.json` (change plans; step bodies and arguments are customer data and encrypted with each app's own key).
- Maps are re-sanitized when `sezgi mcp`, `sezgi sun` or `sezgi ayna` loads them, so a map committed by someone else cannot inject control or bidirectional characters.
- Ayna listens on 127.0.0.1 only, checks the `Host` header (DNS rebinding), and every `/api/` route, reads included, requires the key generated for that launch (in the address Ayna prints); its token routes also check `Origin` (CSRF). Its page has no inline script or style (CSP `script-src 'self'; style-src 'self'`) and writes map values only as text nodes, so a hostile map cannot run script. Each connection has a total deadline for reading the request. `sezgi sun` also listens on 127.0.0.1 only, checks `Host` and `Origin`, requires a JSON content type and sends no CORS headers.
- Git refs: `HEAD`, refs and `packed-refs` are read only when their real path stays inside `.git`, and only a commit hash is written to the card.
- Signature trust: a key shipped with the card proves integrity, not identity. Trust anchors live in the user's configuration directory: keys pinned with `sezgi anahtar sabitle` (`guvenilen-anahtarlar.json`; only these give a trusted / green status, a different key for the same application is rejected) and keys first seen by `sezgi dogrula` (`gorulen-anahtarlar.json`; a later different key is reported as changed). Ayna only reads these files.

## Spring Boot configuration

- Of `application.properties` / `.yml` only a few keys are read as data: the context and servlet paths, Jackson's naming and root-wrapping settings and auto-configuration exclusions. Placeholders are never resolved from the environment (only a default written in the placeholder, `${X:/api}`, is used) and no profile other than the default document is applied. `pom.xml` / `build.gradle` are read as text to recognise Spring Boot, Spring Security and springdoc; no build tool runs.

## Kotlin and Ktor configuration

- Kotlin sources are parsed, never compiled or run; no Gradle or Maven build runs and no Kotlin script (`build.gradle.kts`, `settings.gradle.kts`) is evaluated: build files and `gradle/libs.versions.toml` are read as text to recognise Spring Boot, Ktor, the serializer (kotlinx.serialization, Jackson) and the app's name and version. Of `application.conf` / `.yaml` only `ktor.deployment.rootPath` is read; an environment substitution (`${?ROOT_PATH}`) is never resolved. Route functions and wrappers are followed with cycle detection and a depth limit.

## ASP.NET Core project files

- `.csproj` files are read as text to recognise the Web SDK, the app's name and version, `<Nullable>` and project references; no build tool (`dotnet`, MSBuild) runs, no NuGet package is restored and no `Directory.Build.props` or imported target is evaluated. Build output (`bin/`, `obj/`), generated files (`*.g.cs`, `*.Designer.cs`), EF Core migrations and test projects are not read.

## Observation

- **What is kept:** for every observed request only its shape: method, path template (value-like segments replaced by `:param`), status code, top-level field names and JSON types of request and response bodies, and query parameter names. Body and query values, headers (`Authorization` included), cookies, tokens and e-mail addresses are never stored; keys that do not look like names are only counted. Of a HAR file only its SHA-256 is kept. Live mode records the requests it sent without the human or the token.
- **Browser scenario** (`sezgi gozlem senaryo`): runs only with `--onayla`, an isolation declaration, `--calistir`, `--sahibiyim` and `evet` typed in a terminal. The CDP address, the start address and every navigation address must be loopback (`127.0.0.1`, `localhost` or `[::1]`); Sezgi does not start a browser, it connects to one the user opened. Values the scenario fills are never written in the scenario file: they come from environment variables or files and reach REA only as secrets in its own process environment (not in its input file, the command line or the evidence). The temporary input file is owner-only and deleted after the run. The page's own code runs in the user's browser and the scenario may change the application it runs against.
- **Entity observation** (`sezgi santral varlik-gozle`): asks for confirmation (`--evet` without a terminal), reads only test-copy targets in `okuma` or `yazma` mode with the human's own session, matches values in memory and stores only counts and the match rate; the read is written to the request log without values.

## External processes (REA)

- REA is an optional tool; Sezgi does not ship it. The user installs it with `sezgi rea kur` (below) or points `SEZGI_REA` at an installation; the bridge looks in `SEZGI_REA`, then in Sezgi's own folder, then on `PATH`. Wherever it is found, before running any REA code the bridge checks the installed package name and version (6.7.0), the npm integrity (sha512), the SHA-256 of REA's tool-effect table and REA's own version and tool list; if any does not match, the bridge stays closed and says why.
- Every command Sezgi calls is classified from the pinned tool-effect table: **automatic** commands only record evidence; **approved** commands (start a process, write files or reach the network, a browser on this computer included) need `--onayla`, an isolation declaration (`--yalitim konteyner|vm|yok`) and `evet` typed in a terminal; **dynamic** commands (run or change the target) also need `--calistir` and `--sahibiyim`. Without a terminal no approval can be given and the command does not run. A command or tool missing from the table is refused. `sezgi kesfet --yetenekler` shows the class and effects of each command.
- REA is started without a shell (`node <script> <tool> <artifact> --format json`), in the temporary directory, with a time limit (120 s by default, `SEZGI_REA_SURE`; 180 s for a browser scenario) and a memory limit (2048 MB, `SEZGI_REA_BELLEK`); a process that exceeds them is killed. Its output goes to a temporary file that is deleted after reading. Only the shape is projected (names, signatures, call targets, counts, request shapes); string contents, page tool descriptions, terminal output and decompiled code are not kept. Output of commercial engines (IDA, Hopper, JEB) is marked not shareable and never enters the card or the evidence bundle.
- An observation made with `--yalitim yok` is stamped at most `inferred`. Process observation runs the target itself: run it only on software you own, preferably in a container or VM.
- **Installing REA** (`sezgi rea kur`): nothing is downloaded or written before the human, after being shown the package, version, license, source, integrity and target folder, types `evet` in a terminal; without a terminal nothing is installed. The target is a private folder in the user's configuration directory (`%APPDATA%\sezgi\rea` on Windows, `$XDG_CONFIG_HOME/sezgi/rea` or `~/.config/sezgi/rea` elsewhere). Sezgi writes a `package.json` pinned to exactly 6.7.0 and its own lockfile for the whole dependency tree (every package with a sha512 integrity from the npm registry) and runs `npm ci --prefix <folder> --ignore-scripts --no-audit --no-fund` without a shell: npm cannot install anything that is not in the lockfile or does not match its integrity, and no package install script runs (a package that needs one, such as the optional Frida binding, stays inactive). The network is used only by this npm step, through the registry npm is configured with. When npm finishes, the bridge's pinning checks run on the folder (package name and version, npm integrity, tool-effect table digest, `rea --version` and the declaration of the tools Sezgi uses); if npm fails or a check does not match, the folder is deleted. `sezgi rea kaldir` asks for confirmation and deletes only a folder whose `package.json` Sezgi wrote.

## Threat model

- Sezgi protects the application from an AI agent that reaches it **through Sezgi's MCP server**: the agent sees and calls only what its token allows, cannot open writes on real data, cannot make tokens and cannot approve its own requests; role claims and approval-looking arguments it sends are ignored.
- **Human proof on real data: system anchor + human password.** A program with **shell access under the same user account** (a coding agent allowed to run commands, or a script) can run `sezgi` inside a pseudo-terminal (for example with `script`), so a terminal is not proof of a human, and it can edit every file in the user's config folder. On real data Sezgi therefore asks for a password only the human knows. An administrator sets it once (`sudo sezgi insan kur --sistem`; on Windows `sezgi insan kur --sistem` in a terminal run as administrator). The password is stretched with PBKDF2-HMAC-SHA256 (600,000 rounds, 16-byte random salt) into an Ed25519 seed; only the salt, the round count and the public key are written, to the **system anchor**: `/etc/sezgi/insan-<uid>.json`, which must be a regular file owned by root, in a folder owned by root, neither writable by group or others; on Windows `<system drive>\ProgramData\sezgi\insan-<user>.json`, which must be owned by Administrators or SYSTEM and must not be writable by the process reading it, in a folder owned by Administrators or SYSTEM; the access lists of the folder and the file must not give anyone but Administrators and SYSTEM a right to change them (write, add or delete files, change permissions or owner). The Windows setup enforces this itself: if the folder already exists with another owner (a user who created `ProgramData\sezgi` before the administrator, so that it inherits the user's "create files" and CREATOR OWNER rights), it makes Administrators the owner; it then cuts inheritance and writes an explicit access list on the folder and on the anchor file (Administrators and SYSTEM full control, Users read only). If that fails it stops with the reason and asks the administrator to take the folder over (`takeown /F <folder> /A /R`) or delete it. The user name and the system drive come from the OS, not from environment variables. A file the user owns is never an anchor (`SEZGI_CAPA_KLASORU` is looked at only when the default location has no file, and its file must pass the same ownership checks, so pointing it at a folder the agent controls does not help). Without a valid anchor, writes on real data stay off.
- Every human step on real data asks for the password in the terminal (echo off) and checks it against the anchor's public key: opening real data, making a real-data token, every approval (`sezgi onay ver`, `sezgi plan onayla`), changing the hourly limit and re-declaring a real-data address as a test copy. With an anchor in place, declaring any test copy and confirming roles (`sezgi oturum ac --rol`, OIDC claims, `--rol-ucu`) also ask for it. The records these steps leave (the target record with its address, kind, remembered real-data addresses and hourly limit; real-data tokens; roles) are signed with the password's private key and verified with the anchor's public key before every write and at approval. A record changed without the password fails verification and its permission is ignored: writes there stay off (fail-closed) and `sezgi hedef`, `sezgi canli` and `sezgi doktor` say why. Approvals on real data are logged with `insan_kaniti: parola` and the anchor's fingerprint.

  | Attack by a program with shell access under the same account | Before (0.1 terminal check) | Now (system anchor + password) |
  |---|---|---|
  | Open real data in a pseudo-terminal (`script -qec "sezgi hedef <url> --gercek-veri"`, typing the app's name) | opened | refused: the password is unknown; without an anchor real data cannot be opened at all |
  | Make a real-data token in a pseudo-terminal (typing `evet`) | made | refused: password |
  | Approve its own queued request in a pseudo-terminal (typing `evet`, or the method and path) | sent to real data | refused, nothing sent: password |
  | Edit `ayar.json`: point the real-data target at another server, raise the hourly limit, or relabel real data as a test copy | took effect | signature fails: writes stay off until the human opens the target again with the password |
  | Edit `tokenler.json`: mark a token as a real-data token or widen it | took effect | signature fails: the token only reads on real data |
  | Declare the real server a test copy (`sezgi hedef <url> --test-kopyasi`, terminal or not) | possible for an address never opened as real data | needs the password when an anchor is set up |
  | Declare a role in a pseudo-terminal, or write roles into `oturum.json` | counted as a verified role | not counted when an anchor is set up (roles must be signed) |
  | Delete or replace the anchor and set its own password | (no anchor existed) | not possible without administrator rights; a user-owned copy elsewhere is rejected |
  | Create the anchor folder before the administrator's setup (Windows `C:\ProgramData\sezgi`) so that the anchor inherits rights for the user | — | setup takes the folder over and rewrites its access list; an anchor whose folder or file the user can change is invalid (writes on real data stay off), which is a denial of service, not a bypass |
  | Replay an older record the human once signed (for example a test-copy declaration the human later replaced) | — | **not stopped**: the files have no rollback protection; every real-data write still needs a fresh approval with the password |
  | Learn the password (keylogger, screen capture, the human pasting it into the agent's terminal, a file or an environment variable) | — | **not stopped**: whoever knows the password is the human for Sezgi |
  | Run as administrator / root (or with UAC set to never notify), or get the human to approve an elevation prompt | — | **not stopped**: it can rewrite the anchor; a Windows process that can write the anchor treats it as invalid |
  | Read the human's app session that Sezgi stores (OS keychain or owner-only file) and call the application directly, without Sezgi | — | **not stopped**: Sezgi cannot guard calls that do not go through it; use short sessions, OIDC with `--hedef-kitle` for a narrow token, and run the agent as a separate user |
  | Brute-force the password offline from the anchor (readable by local users) | — | slowed by 600,000 PBKDF2 rounds; use a long password (at least 12 characters are required) |
  | Replace the `sezgi` binary or a wrapper in `PATH` to capture the password the next time the human types it | — | **not stopped**: run Sezgi from a location the agent cannot write, or run the agent as a separate user |

  In short: the anchor turns "a terminal is attached" into "someone who knows the human's password typed it", which an agent confined to the user's own account cannot fake or reset. It is not a defence against a compromised account or administrator. The strongest setup remains running the coding agent as a separate OS user that cannot read your config folder or keychain.
- When Sezgi asks for a human step and sees a pseudo-terminal or a known coding agent among its parent processes (Linux, macOS) or in the environment, it prints a warning. This is information, not a gate: no warning does not mean that a human is there.
- **Without an anchor** (test copies only): a role declared with `sezgi oturum ac --rol` counts as verified only when it is declared in a terminal, and approvals on a test copy are taken in a terminal or bound to the digest with `--ozet`. This stops a plain script and an agent connected over MCP, not a program with shell access; a test copy is, by declaration, not real data.

## Live mode

- **Gates:** a request is forwarded only in `okuma` / `yazma` mode, with a token permitting the operation (only its SHAKE256 hash is stored; closed by default, expiring, revocable; a pattern opening writes on everything needs explicit confirmation), to the declared target. Writes additionally need `yazma` mode, a target declared as a test copy or opened for real data (a remote target must be `https://`, certificates are verified against the OS trust store and verification cannot be turned off), a fresh map (source files compared by content), a Benlik Card that has not expired (a card without `x-expires_at`, with an unreadable one, or that cannot be read counts as expired, so removing the member does not open writes), a preview that does not reject the request, a human session and a log that accepts the request.
- **Real data:** writes on real data need a valid system anchor and are opened only in a terminal (`sezgi hedef <url> --gercek-veri`, after the human types the app's name and the human password); without a terminal or an anchor the command is refused, and no environment variable or flag opens it. The target record is signed with the human key; an edited record closes writes. This feature is experimental (see *Threat model*). Only a token made in a terminal with `--gercek-veri` and the password (its record signed) may write there; older tokens only read. There are no automatic writes: every write waits for approval, which is accepted only in a terminal (an explicit "evet"; method and path typed for a destructive request; then the human password) and never with `--ozet`. Before queueing and again at approval the card must be signed with a valid signature that does not contradict a pinned or previously seen key and must contain the operation, the map must be fresh and checkable, and the preview must have checked every known rule. At most 20 real-data writes per hour (`--saatlik-yazma <1-200>`, terminal only, with the password). Real-data writes are logged with `gercek_veri: true`. An address once opened for real data is remembered (the same server written differently, such as `localhost` for `127.0.0.1`, a default port written out, another scheme or path, counts as the same address) and can be declared a test copy again only in a terminal (after the human types the app's name and, with an anchor, the password); a request queued on real data keeps the real-data rules at approval even if the target changed. The approval text shows whether the operation looks reversible (inferred from source at most); Sezgi takes no backup and cannot undo a write. The terminal check alone proves only that a terminal is attached; on real data the password checked against the anchor is the proof (see *Threat model* for what it does not stop).
- **Change plans** (switchboard MCP tool `plan`) only record steps; nothing runs until the human approves a step with `sezgi plan onayla`, and every step passes the same gates and approval rules as any other write. A plan's arguments or an agent's role claims cannot open a gate.
- **Human approval:** destructive writes always; every write that reaches outside the application (an outgoing HTTP write, e-mail, payment, queue or cloud call found in its call chain) or that cannot be undone (a hard delete, cascades included), every write whose external effect is unknown (its call chain, followed over the function call graph with polymorphic candidates, has a library call Sezgi cannot classify, a dynamic call such as reflection, an index or `getattr` choice or `send`, too many candidate targets, or is cut at the depth limit: fail-closed), every delete or soft delete whose reversibility is not shown, and every write that changes credentials (a password, token, API key, secret or two-factor setting, named by its path or function) whose reversibility is not shown; and every write whose evidence is not certain or is contradicted by other evidence (for example a HAR capture), whose preview could not check every known rule (an object-level access check or ownership comparison found anywhere in the call chain counts as not checkable, and so does a write on a record whose call chain could not be resolved completely, or a conditional rejection whose status code is not known), or that needs a role the human does not hold as a verified role, waits for `sezgi onay ver` run by the human. The reversibility verdict (yes / partly / no / unknown) and the outgoing calls are inferred from source (at most `inferred`); a missing finding does not mean the operation has no external effect. Library calls are classified by package from a fixed, general table; Ruby has no imports and C# imports name spaces, so there only packages in the table count and an unknown constant or type is not treated as unclassified; a function passed in as a parameter (a callback such as `next()`) is not counted as a dynamic call; a method called on an object whose type is unknown and whose name no project method has is not followed. The reversibility claim is deliberately not required to be `certain` for a write to go without approval: reversibility is always an inference, so requiring it would send every write to approval; instead the rule is one-sided and only tightens (an external effect, "no", or a delete or credential change whose way back is not shown always waits for approval). Verified roles come only from the human's own declaration (`sezgi oturum ac --rol`, made in a terminal; a declaration without a terminal is ignored; with a system anchor, roles from every source count only when signed with the human password), a claim in an OIDC ID token whose signature was verified, or the application's own "current user" endpoint read with the human's session; a role claimed by the agent is removed before the preview and never trusted. The approval is bound to the method, address and body digest shown by `sezgi onay goster`; every gate is checked again at approval time and concurrent approvals send a single request.
- **Secrets and customer data at rest:** the human session and the log key are kept in the OS keychain on Windows (Credential Manager) and macOS (Keychain); on Linux, and where no keychain is available, in owner-only files (folders `0700`, files `0600`). The request log (hash-chained, without parameter values), the bodies and arguments of requests waiting for approval and the responses kept by the experience memory (`sezgi hafiza`, off by default) are encrypted with ChaCha20-Poly1305. A chain does not stop someone with write access to the config directory from rewriting the whole log. Live-mode state is protected by a cross-process lock.
- Private signing keys are stored in the user's configuration directory (`%APPDATA%\sezgi\anahtarlar` on Windows, `$XDG_CONFIG_HOME/sezgi/anahtarlar` or `~/.config/sezgi/anahtarlar` elsewhere, macOS included), created owner-only on Unix, and must never be written into a project directory.

## Network

Sezgi runs locally and sends no telemetry. It makes network requests only:
- to the target configured with `sezgi hedef`, in `okuma` / `yazma` mode, when an agent calls `cagir` or an operation tool, or a human runs `sezgi onay ver`, `sezgi plan onayla` or `sezgi santral varlik-gozle` (the latter only to test-copy targets);
- to the identity provider configured with `sezgi oturum ac --oidc` (discovery, device flow, token and key endpoints, token exchange, and refresh-token renewals while the session lasts);
- to the application's own "current user" endpoint, when the human chose `sezgi oturum ac --rol-ucu`;
- to the npm registry npm is configured with, through npm, only during `sezgi rea kur` and only after the human typed `evet` (REA's pinned package and its dependencies);
- to a browser on this computer (a loopback CDP address the user gives), through REA, for `sezgi gozlem senaryo` and `sezgi kesfet --webmcp`. The scenario's page then talks to the application on this computer; the page's own code runs in the user's browser and Sezgi does not control its requests.

`sezgi init`, `sezgi kesfet` without `--webmcp` (also with `--rea`: REA runs locally, Sezgi passes it no network access of its own; a target started for process observation runs with whatever access its environment gives it, so use a container or VM), `sezgi gozlem al`, `sezgi mcp` without a token, `sezgi ayna` and `sezgi sun` make no network requests. Any other network activity is a bug.

## Signatures

- A Sezgi signing key should be used only for Benlik Cards and Sezgi's shared maps. Signatures use separate FIPS 204 contexts: `benlik-card` for cards, `benlik-evidence` for evidence bundles and `sezgi-paylasim` for shared maps, so a signature made for one purpose is not valid for another or for anything else.
- Shared maps (`.sezgi/paylasim.bin`) come from the repository and are untrusted: `sezgi init` uses one only if it is signed with a key the user pinned for the application, the Sezgi and adapter versions match and every source file is byte-identical (SHA-256); otherwise it maps from code.
- The ML-DSA implementation used (RustCrypto `ml-dsa` 0.1.x) has not yet had an independent audit. An independent security review is planned before 1.0.
