# Sezgi: detailed reference

*Sezgi is Turkish for intuition: knowing without thinking.*

Sezgi gives an application a self. It reads the application's code once, extracts its endpoints with their inputs, validation rules and auth requirements, and serves that knowledge to AI agents over MCP. Agents stop scanning code and start asking. Sezgi also writes a **[Benlik Card](https://github.com/benlik-spec/benlik-spec/blob/main/SPEC.md)** (signable with `--imzala`): the application's machine-readable self-description.

> **Status: 0.1, experimental.** TypeScript + NestJS, Python + FastAPI, Django (with Django REST Framework) and Flask, JavaScript / TypeScript + Express, Fastify, Next.js, Java / Kotlin + Spring Boot, Kotlin + Ktor, Ruby on Rails, C# + ASP.NET Core, Go + net/http, Gin, Echo, Chi, Fiber, gorilla/mux and PHP + Laravel (see language quality levels below). Read-only by default: Sezgi calls your application only in the opt-in live mode, which writes only to a declared test copy or, experimentally, to real data opened in a terminal (every step there needs the human's password, checked against a system anchor that only an administrator can set up, so an agent with shell access under the same account cannot open, approve or re-sign it without the password; it does not stop a program that learns the password or runs as administrator: see the threat model in SECURITY.md), or through a browser scenario you write and approve, which runs only against an app on this computer and may change it.

> **Security note.** Text that Sezgi extracts from code (summaries, field names, rule texts) is passed to AI agents as data. A malicious repository can put instructions there. Sezgi strips control characters, limits length and tells the agent not to follow such text, but agents should treat any code-derived text as untrusted.

## Why

**Public, reproducible benchmark** ([`kanit/acik`](https://github.com/atabaykut/Sezgi/tree/main/kanit/acik), one command, pinned commits). Ground truth is each application's own official OpenAPI file, written by its maintainers:

| Application (commit) | Endpoints found | Extra (not in the doc) | Auth | Body fields |
|---|---|---|---|---|
| Immich server (`aec0dd1`, 61,567 lines) | 279/279 | 16 | 100% | 437/485 |
| Cal.com API v2 (`54343aa`, monorepo) | 121/121 | 41 | 99.2% | 250/250 |

Immich was last measured on 2026-10-21 with Sezgi 0.1.0; Cal.com on 2026-10-14 with an earlier 0.1.0 build (its repository was not available for the later run). Parsing and map time on the benchmark machine (Windows 11, `olc.sh`): Immich 172 ms first run and 186 ms second run, Cal.com 204 ms and 212 ms (2026-10-14), with the repositories already in the operating system's file cache. These are the `Süre` (time) line of `sezgi init`: discovery, parsing and the adapter; writing the map, the evidence store, the graph, the card and the evidence bundle is not included. Measured the same way right after a fresh clone, the first run took 1215 ms (Immich) and 1899 ms (Cal.com) ([`OZET-duzeltme-oncesi.md`](https://github.com/atabaykut/Sezgi/blob/main/kanit/acik/sonuc/OZET-duzeltme-oncesi.md), before the correction round).

Read these numbers carefully:
- **They measure recall against the docs.** "Extra" endpoints exist in the code but not in the official document (for example a maintenance server, health checks); they are not scored. The comparison counts one endpoint per address, so further endpoints sharing an address (API versions, a secondary app) are not shown: Sezgi maps 306 endpoints in Immich and 177 in Cal.com in total. Body fields are scored only where the document gives a named schema; inline body schemas are not scored.
- **The adapter was tuned on these apps.** Measured before any change, the first numbers were: Immich 84.9% endpoints, 0% body fields; Cal.com 96.7% endpoints, 52.1% body fields. The numbers above come after adding general NestJS capabilities. A held-out app was then measured untouched (below).
- **Held-out app (Ghostfolio, measured once with the frozen adapter, n=1):** endpoints 120/120 with no extras; auth 88/120 (73.3%) after manual adjudication (the independent referee scored 22/120). All 28 endpoints Sezgi wrongly called public were stamped *inferred* (an unrecognized global guard), so writes stay locked and `onizle` does not say PASS; 4 OAuth entry points were wrongly called login-required with a *certain* stamp. Inferred auth decisions were right in only 18 of 46 cases: treat `[Yorum]` (inferred) as unknown, not as likely. Table links: precision 100%, recall 80.3%. Body fields could not be checked independently (the referee resolved 3 of 27 schemas). Details: [`kanit/SONUC-5-holdout-ghostfolio.md`](https://github.com/atabaykut/Sezgi/blob/main/kanit/SONUC-5-holdout-ghostfolio.md).
  - *Caveats:* these numbers describe the code before the correction round. The adapter rule file was frozen, but the adapter engine (`adaptor.rs`) changed between the freeze and the pre-registration and that version was not kept, so the claim "inference logic unchanged" cannot be verified ([`kanit/DUZELTME-NOTU-1.md`](https://github.com/atabaykut/Sezgi/blob/main/kanit/DUZELTME-NOTU-1.md)). A new held-out app under version control is planned.
  - *Regression test after the correction round (not held-out):* auth 92/120 with the same adjudication rule; certain-stamped auth decisions right in 70 of 70 (before: 70 of 74, the 4 OAuth entry points). After composed-decorator support: auth 120/120, certain-stamped decisions right in 98 of 98. [`kanit/SONUC-6-ghostfolio-gerileme.md`](https://github.com/atabaykut/Sezgi/blob/main/kanit/SONUC-6-ghostfolio-gerileme.md).
- The single Cal.com auth difference is a gap in Cal.com's document: the code protects the endpoint with `@UseGuards(ApiAuthGuard)`.

**Agents.** Same model, same tasks, answers scored against a key derived from the official OpenAPI. On Immich (16 tasks, one model, one run): reading code 14/16 at 39.5k tokens per task, the official OpenAPI 15/16 at 43.6k, **Sezgi 16/16 at 20.5k**.

**Real writes.** On an Immich test copy (6 write tasks, 2 runs each, one model, pre-registered), the agent got the operations the token allows as their own tools: **12/12 at 3.8 turns and $0.20 per task**. With only the search-style tools (`ara` → `tani` → `cagir`): 11/12 at 6.3 turns and $0.23. Every result was checked against the app's own state, not the agent's claim. `kanit/SONUC-11-islem-araclari.md`.

Method, caveats and raw results: [`kanit/`](https://github.com/atabaykut/Sezgi/tree/main/kanit).

FastAPI auth follows the same rule as NestJS: a decision is certain only when the dependency chain (`Depends`, `Security`, `Annotated[...]` aliases, router and app `dependencies`) reaches a security scheme such as `OAuth2PasswordBearer` or `HTTPBearer`. Database links for Python come from SQLModel / SQLAlchemy usage: tables are classes with `table=True` or `__tablename__`; reads are `select(M)`, `.get(M, …)`, `.query(M)`; writes are objects added to or deleted from the session (their model taken from the parameter type, an `Annotated[...]` alias or the return type of the function that produced them) and `update/insert/delete(M)`; project calls are followed 3 levels; raw SQL marks the list as possibly incomplete. Stamped inferred, like NestJS. Class-based views (`@controller(router)`, fastapi-utils `cbv`) are read; a place where routes are registered but cannot be read is reported as an unreadable route source (file:line) by `init`, `rapor`, `doktor`, Ayna and the card, and the coverage is then partial.

Django routes start at the settings' `ROOT_URLCONF` (the settings module is the `DJANGO_SETTINGS_MODULE` in `manage.py`, star imports followed) and follow `include(...)`: `path` converters become typed path parameters, `re_path` / `url` named groups become parameters (a pattern that cannot be turned into a path completely is flagged), `urlpatterns += ...` under `if settings.DEBUG:` is a conditional route, and Django REST Framework routers expand ViewSets into their actions and `@action`s. A DRF auth decision is certain when the permission classes are known (`IsAuthenticated`, `AllowAny`, `IsAdminUser`, `IsAuthenticatedOrReadOnly` per method, `&` / `|` combinations, otherwise the settings' `DEFAULT_PERMISSION_CLASSES`); so are Django's `@login_required`, `@permission_required`, `LoginRequiredMixin`, `PermissionRequiredMixin` and the same wrappers in urls.py. A project permission class or decorator read from its body is inferred, and `get_permissions` choosing classes at run time leaves the decision unknown. A project decorator that reads an API key or a token from the request (headers, `META`, query or body) and answers 401 / 403 requires login too (inferred; the guard is marked `[api key/token]`). A function view's methods come from `@require_POST`, `@require_GET`, `@require_http_methods`, DRF `@api_view([...])`, a project decorator that compares `request.method` and answers 405 (`@allow_methods("POST")`) or a leading `if request.method != "POST": return HttpResponseNotAllowed(...)`; only a view without any of these is listed as GET plus the methods its body compares. Bodies and responses come from serializers (a ModelSerializer's fields from the model, `read_only` / `write_only`, `extra_kwargs`, request envelopes such as `request.data.get("user")`) and Django forms; tables from Django models (`Meta.db_table`), with `on_delete=CASCADE` (also in migration files) and signal receivers (`post_save`, `pre_delete` and others) as events.

Flask routes follow `register_blueprint` from the app, also inside factories and helper functions (a `url_prefix` given at registration replaces the blueprint's own), `MethodView` / `add_url_rule`, Flask-RESTful, Flask-Smorest and Flask-RESTX. Flask-Login, Flask-JWT-Extended, Flask-HTTPAuth and Flask-Security decorators are certain; project decorators and `before_request` hooks are inferred. Bodies come from marshmallow schemas (including `pre_load` envelopes), Pydantic models, reqparse and RESTX models, or else the keys the handler reads (types unknown); tables from Flask-SQLAlchemy models.

**Spring Boot** is found from `pom.xml` / `build.gradle(.kts)`. Routes come from `@RestController` / `@Controller` classes: the class `@RequestMapping` prefix joined with `@GetMapping` … `@DeleteMapping` or `@RequestMapping(method = …)` (path arrays, constants such as `ApiPaths.USERS`, mappings declared on an implemented interface or a base class), behind `server.servlet.context-path` from `application.properties` / `.yml`. Inputs: `@RequestBody` DTO classes and records, `@PathVariable`, `@RequestParam`, `@ModelAttribute`, `Pageable`; Jakarta Validation constraints (`@NotNull`, `@NotBlank`, `@Size`, `@Min`, `@Email`, `@Pattern` …) count only when the parameter carries `@Valid` / `@Validated` (otherwise the fields are not required and the operation says why), nested constraints only through `@Valid` fields, a project constraint annotation is listed as a rule the preview cannot check, and `@JsonProperty`, `@JsonIgnore` and `UNWRAP_ROOT_VALUE` with `@JsonRootName` shape the JSON. Login and roles: the `SecurityFilterChain` bean (or `WebSecurityConfigurerAdapter`), first matching `requestMatchers(…)` rule with `permitAll()`, `authenticated()` or `hasRole(…)`, and method security (`@PreAuthorize`, `@Secured`, `@RolesAllowed`, counted as certain only when `@EnableMethodSecurity` turns them on). A rule read from its definition is certain; a matcher or SpEL expression that cannot be resolved makes the decision `varsayim_bilinmeyen_guard`; with Spring Security on the classpath but no chain, the Spring Boot default (every request needs login) is inferred. The response is the handler's return type (`ResponseEntity<T>`, `Optional<T>`, lists unwrapped). Database links come from Spring Data repositories (`save` / `delete*` write, `find*` / `count*` read, `@Modifying @Query` writes) and `EntityManager`, followed through services and interface implementations; cascades from `@OneToMany` / `@OneToOne` with `cascade = ALL | REMOVE` or `orphanRemoval`, and `@OnDelete(CASCADE)`; `@SQLDelete` / `@SoftDelete` make a delete reversible. Inferred, like NestJS. A project annotation that an `@Aspect` cuts (`@Around("@annotation(ApiKeySecured)")`) is an unrecognized guard. Kotlin sources (`.kt`) are read by the same adapter: `object` and top-level constants and string templates (`"$API/books"`), `data class` DTOs, the Kotlin Spring Security DSL (`http { authorizeHttpRequests { authorize("/x", permitAll) } }`), `?: throw` and `orElseThrow { }`. Kotlin's own rules apply: a Bean Validation constraint written on a constructor property without a use-site target goes to the constructor parameter and does not validate the field (`@field:NotBlank` is needed, and the operation says so, unless the build sets `-Xannotation-default-target=param-property`); with jackson-module-kotlin a non-nullable field without a default value is required (a missing `Int` becomes 0); a `String?` or defaulted `@RequestParam` is optional. Exposed tables are data models, as in Ktor.

**Ktor** is chosen when the build file (or `gradle/libs.versions.toml`) uses the Ktor server (`io.ktor`). Routes are read from the routing DSL: from `routing { }` (and `install(Routing)`) through `route("/x") { }`, the HTTP verbs (`get("/{id}") { }`, `post { }` …), `route(path, HttpMethod.X) { handle { } }` and `method(...)`, into the project's route functions (`fun Route.taskRoutes(service: TaskService)`) with the caller's prefix, behind `ktor.deployment.rootPath` from `application.conf` / `.yaml`. Constants and string templates are followed and type-safe resources (`get<Articles> { }` with `@Resource`) are supported; a registration inside `if` / `when` / a loop is conditional, and one whose path cannot be resolved is listed as a dynamic registration instead of being guessed. Login: inside `authenticate(...) { }` login is required (certain) and `optional = true` stays public; Ktor has no login by default, so a route outside it is public (certain). The project's own wrapper (`withRole("ADMIN") { }`) is opened through its body (`build()` places the caller's routes); a route-scoped plugin (`install(X)`) or an unrecognized wrapper is an unrecognized guard, and the names in its arguments are inferred roles. Inputs: `call.receive<Dto>()` (or a typed local), also when the handler passes `call` to a controller method (`controller.create(call)`); required fields follow the serializer (kotlinx.serialization: a field without a default value is required, `@SerialName` names it; Jackson: non-nullable without a default); path parameter types come from conversions (`toLong()`, `getOrFail<Long>`), `queryParameters["x"]` is the query, `receiveParameters()` a form and `receiveMultipart()` a file upload; a RequestValidation `validate<Dto> { }` is listed as a check the preview cannot run. The response is the payload of `call.respond(...)` (a constructor call or typed local is certain, a service method's return type is inferred) with `HttpStatusCode.Created` as its code; `call.respond(HttpStatusCode.X)` and `throw NotFoundException()` are rejections, with StatusPages `exception<X> { }` mappings applied. Table links come from Exposed (`object Tasks : LongIdTable("tasks")`: `insert` / `update` / `deleteWhere` write, `selectAll` / `select` read, DAO entities through their `EntityClass`; `reference(..., onDelete = ReferenceOption.CASCADE)` is a cascade) and JPA / Spring Data, followed through services. Inferred, like NestJS.

**Ruby on Rails.** Chosen when the `Gemfile` lists `rails` (or `railties` / `actionpack`) and `config/routes.rb` exists. Routes come from `config/routes.rb` and the files it pulls in with `draw :name`: `resources` / `resource` with their seven (six) actions, `only` / `except`, `path`, `param`, `controller`, `module`, nested and `shallow` resources (`/posts/:post_id/comments`), `member` / `collection` and `on:`, `namespace`, `scope`, `controller`, `concern` / `concerns`, `constraints` (the route is conditional and its condition becomes an `env:` node), verb routes (`get 'path', to: 'c#a'`, `'path' => 'c#a'`, `match ... via:`), `root`, and `devise_for` (the Devise endpoints the model's `devise` modules enable, with `controllers:`, `path:`, `path_names:`, `skip:`, `only:`). A route counts only when its controller class and action (a public method or a template) exist, as Rails itself would answer; `mount`ed engines and `redirect` routes are not operations. Login follows the controller's filter chain through ancestors and included concerns in Rails' order (`before_action` / `skip_before_action` with `only` / `except` / `if` / `unless`, Rails 8 `allow_unauthenticated_access`): it is certain when the filter's definition reaches an authentication (Devise `authenticate_<scope>!`, `authenticate_or_request_with_http_token`, `http_basic_authenticate_with`, a 401, a redirect to the login page, or a rejection when there is no user); a challenge made only under a condition is optional (inferred), a conditional filter, a role-only filter or an untraceable filter is inferred. Roles come from role predicates in filters (`current_user.admin?`, `has_role?(:x)`), the Pundit policy method an action authorizes (`authorize @post` → `PostPolicy#update?`) and the matching CanCanCan `Ability` rules; always inferred. Bodies come from strong parameters (`params.require(:post).permit(:title, tags: [])`, `params.expect(...)`): the required key is certain (`ParameterMissing` → 400), field types come from `db/schema.rb`, requiredness on create and limits from model validations (`presence`, `length`, `numericality`, `inclusion`, `format`) and allowed values from `enum`; custom validations, uniqueness and Active Storage attachments are listed as not checkable by the preview. On read endpoints `params[:x]` is the query (requiredness inferred). Responses come from the action's jbuilder template (implicit or `render :show`, partials and `json.array!` followed), a serializer (ActiveModel::Serializers, jsonapi-serializer, Blueprinter) or a `render json:` expression. Table links come from ActiveRecord calls, typed through assignments, associations and scopes, followed through filters, called methods, service objects and the written model's callbacks; cascades from `has_many ... dependent: :destroy` / `:delete_all` and `add_foreign_key ..., on_delete: :cascade`; jobs and mails (`perform_later`, `deliver_later`) become job nodes with what their `perform` deletes. Measured on two public apps against a hand count of their `config/routes.rb` (not held out): RealWorld (Rails 4.2, Devise, jbuilder) 34/34 endpoints, Lobsters 201/201 (redirect routes and the mounted engine left out, duplicate method + path definitions counted once).

**ASP.NET Core** is found from a `.csproj` with the Web SDK (`Microsoft.NET.Sdk.Web`; test projects are skipped) in the folder or up to four levels below it; projects it references with `<ProjectReference>` outside the folder (an infrastructure or domain layer) are read too, inside the repository or solution folder. Routes come from controllers (`[Route]` joined with `[HttpGet("…")]` …, the `[controller]` / `[action]` / `[area]` tokens, `~/` absolute templates, `[ActionName]`, the `Async` suffix dropped, `{version:apiVersion}` from `[ApiVersion]`), conventional routes (`MapControllerRoute`) and Minimal APIs (`MapGet` … `MapMethods`, nested `MapGroup`, groups passed to or returned by extension methods, `HasApiVersion`); a route constraint (`{id:int}`) gives the parameter type, and a route registered under `if (app.Environment.IsDevelopment())` is marked conditional. Inputs follow the framework's binding rules (`[FromBody]`, `[FromQuery]`, `[FromRoute]`, `[FromForm]`, `[AsParameters]`; services from dependency injection are not inputs); DTO and record fields come with DataAnnotations (`[Required]`, `[StringLength]`, `[Range]`, `[EmailAddress]`, `[RegularExpression]` …), `required` members, nullability (a non-nullable reference type is implicitly required under `<Nullable>enable</Nullable>`) and System.Text.Json names (camelCase, `[JsonPropertyName]`). Constraints are rules only where the framework enforces them, in `[ApiController]` controllers: in Minimal APIs without `AddValidation()` and in other controllers they do not run, so only types and `required` are kept and requiredness is a guess. Login decisions are certain when read from a definition: `[Authorize]`, `Roles`, `Policy` (its roles from `AddPolicy(…, p => p.RequireRole(…))`, constants resolved), `RequireAuthorization` on an endpoint, a group or `MapControllers()`, the MVC global `AuthorizeFilter` and a global `FallbackPolicy`; `[AllowAnonymous]` overrides all of them, as in the framework. An endpoint without any marker is public but `inferred`, and middleware that answers 401 / 403 is reported as an unrecognized guard. Database links come from Entity Framework Core (`DbSet` access, `Add` / `Update` / `Remove`, `ExecuteDelete`, changes to a loaded entity followed by `SaveChanges`), followed through services (interface to implementation) and MediatR handlers (`Send`; same-named request types are told apart by namespace and enclosing class); cascades come from `OnDelete(DeleteBehavior.Cascade)` and EF Core's rule that a required relationship cascades. MediatR `Publish` events with their `INotificationHandler<T>` listeners and `BackgroundService` jobs become event and job nodes. Stamped inferred, like NestJS.

**Go** (net/http including Go 1.22 method-and-pattern routes, Gin, Echo, Chi, Fiber, gorilla/mux): the module path comes from `go.mod` (several modules in one repository work; a project without `go.mod` takes its import prefix from its own imports). Routes are read by following the route-setup code in order from `main` and `init` into the project functions it calls: routers passed as arguments, returned by constructors or kept in a struct field, groups and sub-routers (`Group`, `Route`, `With`, `Mount`, `PathPrefix(...).Subrouter()`, `http.StripPrefix`) and table-driven route lists. A route whose path is built at run time is not invented: it is listed under `dinamik_kayitlar` and in `sezgi rapor`; a group whose prefix is built at run time keeps its routes but marks them secondary. Middleware is applied with each framework's ordering rule (Gin and Echo groups take the middleware present when they were created, Fiber follows registration order, Chi, gorilla/mux and net/http wrappers apply to every route). Auth is certain only for a recognized library authenticator (echo-jwt and Echo's JWT / KeyAuth / BasicAuth, Gin BasicAuth, gin-jwt, go-chi/jwtauth `Authenticator`, Fiber jwtware / basicauth / keyauth); a project middleware that rejects with 401 or 403 makes login required (inferred), one that only reads a token and stores the user makes it optional, and a `false` flag that guards every rejection (`AuthMiddleware(false)`) is honoured. Roles come from the string arguments and role comparisons of a middleware that answers 403 (inferred). Request bodies are the struct a handler binds (`ShouldBindJSON`, `Bind`, `BodyParser`, `json.NewDecoder(r.Body).Decode`, binding helpers and validator types with their own `Bind` method): names from `json` / `form` / `query` / `uri` / `param` tags, rules from `binding` (Gin) or `validate` tags when validation is seen (`c.Validate`, `validator.Struct`); without validation, requiredness is reported as uncertain. Query and path parameters come from usage (`c.Query`, `c.DefaultQuery`, `r.URL.Query().Get`, `chi.URLParam`, `r.PathValue`, `mux.Vars`), integer types from `strconv` conversions and route patterns. Table links come from GORM (`Find`, `First`, `Create`, `Save`, `Delete`, `Model(&M{})…`; table names from `TableName()` or GORM naming, `constraint:OnDelete:CASCADE` cascades, deletes of a `gorm.Model` are soft) and from SQL text in database/sql, sqlx and sqlc-style constants, followed 3 levels; inferred.

**PHP + Laravel.** Chosen when `composer.json` requires `laravel/framework` (or `laravel/lumen-framework`). Auth is read from middleware: route, group and controller middleware (`$this->middleware(...)`, `HasMiddleware::middleware()`), the global stack and the `web` / `api` groups (from `App\Http\Kernel` or `bootstrap/app.php` `withMiddleware`) are resolved through their aliases to classes. `auth`, `auth:sanctum` and `verified` (resolving to the framework's `Authenticate` class or one derived from it) and the Spatie `role` / `permission` classes make the decision certain; a project middleware is read from its code (`handle()` and the methods it calls) and is at most inferred; `can:` and `$this->authorize()` / `Gate` are inferred; an alias that cannot be resolved is reported as an unrecognized guard. Roles come from `role:` / `permission:` parameters and, inferred, from the policy or `Gate::define` behind an ability (`hasRole`, `hasAnyRole`, `role === '…'`). Inputs come from a Form Request's `rules()` (including `array_merge(parent::rules(), …)`) or `$request->validate([...])` / `Validator::make`: `required` is certain, `sometimes` and `required_if` make the flag uncertain, nested keys (`meta.source`, `items.*.url`) become nested fields, and rules the preview cannot check (`exists:users,id`, custom rule objects, files) are kept as written and listed. The response comes from an API Resource's `toArray()` with its `data` wrapper; route names (`->name('posts.show')`, resource names) are kept as operation ids. Table links come from Eloquent calls followed through services (`Post::where(...)`, `$post->update()`, relation writes such as `$user->posts()->create()` and pivot `sync()`, `DB::table('…')`), route model binding and `exists` / `unique` rules; cascades from `cascadeOnDelete()` / `onDelete('cascade')` in migrations. Stamped inferred, like NestJS.

**Front ends.** A React, Next.js, Preact, Vue, Svelte (SvelteKit), Angular, Remix (and React Router v7 framework mode) or Solid (SolidStart) front end next to the API is read too: in the app itself, in a `frontend`, `client`, `web`, `ui`, `webapp`, `front` or `app` folder beside or below it (inside the same git repository), or given with `--on-yuz <dir>`. Vue and Svelte single-file components are read in full: the `<script>` blocks and the template's events (`@click`, `on:click`) and links (`<router-link>`, `<a href>`). Angular: `Routes` arrays (`RouterModule.forRoot` / `forChild`, `provideRouter`) with lazy `loadChildren` / `loadComponent`, component templates (`templateUrl` and inline `template`: `(click)`, `(ngSubmit)`, `routerLink`), components used by selector, `HttpClient` calls in services injected through the constructor or `inject()` with base URLs from constants and `environment`. Remix / React Router v7: file routes in `app/routes` (flat routes, folder routes, nested folders) or `app/routes.ts`, `loader` / `action`, `<Form method>`, `useFetcher` and `useSubmit` (a form posts to its route's `action`). Solid: `@solidjs/router` routes (also `lazy(() => import(...))`), SolidStart file routes in `src/routes`, `createResource` / `createAsync`, `query` / `action` wrappers and `"use server"` functions (their calls are followed; the count is in `istatistik.sunucu_fonksiyonu`). Sezgi links screen → UI action → client call (generated OpenAPI client including oazapfts, axios, fetch, Angular `HttpClient`, TanStack Query, RTK Query, SWR) → endpoint; a generated client in a workspace package of the same repository (`"@x/sdk": "workspace:*"`) is followed. A call is `certain` only when it matches one endpoint unambiguously; which action triggers it and what a screen displays are always `inferred`. Screen changes (`navigate(...)`, `router.push`, Angular `router.navigate([...])` and `routerLink` including relative links, `<Link>`, `<A href>`, `redirect(...)` and similar) become `NAVIGATES` edges between screens, always `inferred`. A screen guard (Angular `canActivate` / `canMatch` / `canActivateChild`, Vue `beforeEnter` / `meta.requiresAuth`) gives the screen a login requirement (`giris`: `gerekli`, or `misafir` for a page only for signed-out users such as the login page, or `bilinmiyor`) and a `REQUIRES_PERMISSION` edge to `guard:web/<name>`; it is read from the guard's name and source, so it is always `inferred`. The links go to `.sezgi/web-baglari.json` and into the evidence store and graph below. An app that depends on a back-end framework (NestJS, Express, Fastify, Koa …) is never taken for its own front end, and a front end found automatically that calls no API is left out silently.

**User journeys.** From these links Sezgi builds the journeys that end in an operation, for example `/login › Log In → /items › Save → POST /api/v1/items/`: the operation's screen and action and, when it needs login, the login screen and action first, with the screens in between along the shortest chain of screen changes. Journeys go into the evidence store, the graph and the card (`x-journeys`); `tani` and `etki` show the journeys an operation is part of. A journey read from code is at most `inferred` (conditional rendering, redirects and session state are not known from source). It becomes `observed` when the request sequence was seen at run time (`sezgi gozlem`, below); its UI steps become `observed` only through a browser scenario run in a declared container or VM, never from a network capture alone.

**Without source code** (`sezgi kesfet <folder|file>`): for an application shipped without source, Sezgi reads what the files themselves say, without running anything and without network access: Windows `.exe`/`.dll` identity (machine, subsystem, .NET header, version resource, imported DLLs), ELF identity (class, machine, type), Android APK manifests (package, version, permissions, components), SQLite database schemas (tables, columns, keys, indexes, triggers, views; a foreign key declared in the schema is `observed`, the ceiling for a schema read from a shipped file, and carries its columns and `ON DELETE` / `ON UPDATE` actions; `NOT NULL`, `UNIQUE` and `CHECK` constraints are kept with the table), with no SQLite library and no SQL executed, and Electron packages (`app.asar`, read by a bounds-checked reader): the package identity, the IPC chain from a front-end call through the `contextBridge` bridge to the main-process handler (`ipcMain.handle/on`), window settings (`contextIsolation`, `nodeIntegration`, `sandbox`, `webSecurity`), the front end's network calls (the packaged JavaScript is extracted to a temporary folder, read with the front-end adapter and deleted) and, when the Electron binary next to the package carries them, its fuses.

With `--rea` it also reads .NET members, signatures, call targets and P/Invoke names through REA, an optional analysis tool (npm package `rea-agents` 6.7.0, MIT; needs Node.js 22.19+, 24.11+ or 26+). `sezgi rea kur` installs it into a private folder in Sezgi's configuration directory: it shows the package, version, source, integrity and target folder, asks for `evet` in a terminal, installs the whole dependency tree from a lockfile shipped inside Sezgi with install scripts disabled, then runs the bridge's pinning checks and deletes the folder if anything does not match. `sezgi rea durum` shows the state and `sezgi rea kaldir` removes it. The bridge looks for REA in `SEZGI_REA`, then in that folder, then on `PATH`; it stays closed and says why if the pinned package, its integrity, its tool table or its version do not match (`sezgi doktor --rea` shows its state; it and `sezgi kesfet` suggest `sezgi rea kur` when REA is missing). REA runs as a child process without a shell, with a time and memory limit; its raw output is deleted after reading and only the shape is kept (names, signatures, counts; no string contents, terminal output or decompiled code). Every REA command Sezgi uses has one of three classes, taken from REA's pinned tool-effect table, and a command that is not in the table is refused:
- **automatic** (only records evidence): runs with `--rea`;
- **approved** (starts a process, writes files or reaches the network, a browser on this computer included): runs only with `--onayla`, an isolation declaration (`--yalitim konteyner|vm|yok`) and `evet` typed in a terminal; without a terminal it does not run. This covers native binaries (ELF and native PE) through a Ghidra, IDA or Hopper you installed (function and symbol lists, a summary of decompiled entry functions), firmware regions through Binwalk (Linux only, `REA_BINWALK_COMMAND`), REA's Electron JavaScript analysis, and WebMCP discovery (`--webmcp <127.0.0.1 CDP address> [--kaynak <origin>]`: the tools a page in a browser you opened declares; only names and schema skeletons, none is called, and Sezgi neither starts a browser nor connects to a remote address);
- **dynamic** (runs or changes the target): also needs `--calistir` and `--sahibiyim` (you own the target). Process observation runs a single ELF file briefly, in a temporary folder; it is not supported on Windows.

`sezgi kesfet --yetenekler [--json]` lists each REA command Sezgi uses with its class, its effects and whether it can run on this computer. The output of commercial engines (IDA, Hopper, JEB) cannot be shared: it stays in the local evidence store and never enters the card or the evidence bundle. An observation made without isolation (`--yalitim yok`) is at most `inferred`.

The result goes to `<dir>/.sezgi`: `kaynaksiz.json` (evidence, plan, unknowns) and, as with `init`, the evidence store, the graph, a map and a Benlik Card (with `--imzala`, signed), so `sezgi mcp`, the switchboard and `sezgi dogrula` work for such an app too. The card lists no operations; capabilities, screens and WebMCP tools are `x-` members, each requiring approval. Facts read from shipped files are at most `observed` (from heuristics and decompiled code at most `inferred`) and every fact is marked as possibly incomplete: the preview never passes for a system without source, so every write to it needs human approval.

## How Sezgi differs

- **From OpenAPI generators (e.g. NestJS Swagger):** no running app and no annotations needed; every fact has a source line and a stamp; unknowns are reported as gaps; requests can be checked before sending (`onizle`); endpoints are linked to database tables and front-end screens; the card can be signed.
- **From OpenAPI-to-MCP wrappers:** they are only as good as the document. On Immich, whose document is rich, they come close on accuracy (15/16 against 16/16) but spend about twice the tokens. Measured with a generic OpenAPI tool server built for the benchmark (`kanit/b-mcp.js`), not a third-party product.
- **From code-graph tools:** they index symbols; Sezgi extracts the application's contract (inputs, rules, auth, tables) in the framework's own terms, and keeps the evidence for every claim.

## Quick start

**In 5 minutes,** in your app's folder:

```sh
npx sezgi init        # reads the code, writes the map to .sezgi/ (a few seconds on a large app)
npx sezgi connect     # connects your AI tool; asks tool by tool, `sezgi remove` undoes it (= sezgi bagla)
                      # now ask your AI: "how do I start a refund in this app, what does it need, who may do it?"
npx sezgi mirror      # in the browser: what your app is, what each operation affects, what Sezgi can do here and what it does not know
npx sezgi watch       # keeps the map current as the code changes (= sezgi izle)
```

`npx sezgi` with no arguments says where you are and what to do next and points to Ayna, which also opens before any map exists; if something is wrong, `npx sezgi doctor` says what is missing and the command that fixes it.

**Commands** (`sezgi help` prints the same list; most commands also have an English name):

| Group | Commands |
|---|---|
| Start | `init` · `kesfet` (`discover`) · `izle` (`watch`) · `doktor` (`doctor`) |
| Connect to AI | `bagla` (`connect`) · `kaldir` (`remove`) · `mcp` · `sun` (`serve`) · `santral` (`switchboard`) |
| Look | `ayna` (`mirror`) · `rapor` (`report`) · `karsilastir` (`diff`) · `olc` (`measure`) · `gozlem` (`observe`) |
| Live mode | `canli` (`live`) · `mod` (`mode`) · `hedef` (`target`) · `oturum` (`session`) · `token` · `onay` (`approve`) · `plan` · `kayit` (`log`) |
| Security and data | `anahtar` (`key`) · `insan` (`human`) · `dogrula` (`verify`) · `defter` (`ledger`) · `unut` (`forget`) |
| Advanced | `hafiza` (`memory`) · `paylas` (`share`) · `rea` · `teshis` (`diagnostics`) |

`sezgi help <command>` prints each command's flags. Details follow.

Install with npm (Node.js 20+). npm picks the prebuilt binary for your platform: Windows x64, macOS arm64 / x64 (macOS 11 Big Sur or later), Linux x64 / arm64 (glibc 2.34+: Ubuntu 22.04+, Debian 12+, RHEL 9+). On Alpine / musl and other platforms, build from source.

```sh
npm install -g sezgi          # or without installing: npx sezgi <command>
sezgi init path/to/app --out ./harita
```

Or build from source: Rust 1.99+ and a C compiler (for tree-sitter); on Windows the binary is `target\release\sezgi.exe`. Point `SEZGI_IKILI` at it to use it through the npm launcher.

```sh
cargo build --release
./target/release/sezgi init path/to/app --dry-run   # what would be written, and why
./target/release/sezgi init path/to/app --out ./harita
./target/release/sezgi mcp ./harita                  # MCP server over stdio
```

`sezgi init` with no folder maps the current directory and ends with the next steps (`sezgi bagla`, `sezgi ayna`, `sezgi izle`). It never edits your AI tools' settings. `sezgi bagla` (`connect`) adds the connection: it lists the AI tools found on this computer, asks about each one separately (nothing is preselected), shows which file changes and warns when a file affects all your projects. Every change is backed up and `sezgi kaldir` undoes it. `sezgi bagla --elle` only prints the lines to add by hand, for example `claude mcp add sezgi -- /abs/path/to/sezgi mcp /abs/path/to/.sezgi`. When Sezgi runs from npm (through `npx` or from a project's `node_modules`), the connection uses `npx -y sezgi@<version> mcp <map>` (`cmd /c npx …` on Windows) instead of the binary's path, which would break when the npx cache or `node_modules` is cleaned; `bagla`, `bagla --elle`, `token olustur` and Ayna suggest the same command. MCP answers follow the output language: `--lang en` (or `SEZGI_LANG=en`, or an English system language) gives English tool names, instructions and every answer, preview details, behaviour summaries, reversibility reasons, meaning summaries and task plans included; Turkish stays the default. Data taken from the app's code (paths, field names, summaries, code expressions) and Sezgi's command names (`sezgi init`) are shown as they are. Both sets of tool names can always be called.

Sign the Benlik Card:

```sh
sezgi key create --name my-key            # ML-DSA-65 key, stored outside the project
sezgi init path/to/app --sign my-key
sezgi verify .sezgi/benlik.json .sezgi/benlik-keys.json
```

`sezgi izle`: after a single-file change the update took 66–83 ms on Immich and 314–319 ms on Cal.com (target < 500 ms; [`kanit/SONUC-7-artimli-guncelleme.md`](https://github.com/atabaykut/Sezgi/blob/main/kanit/SONUC-7-artimli-guncelleme.md), measured with an earlier build).

Commands, the main flags and the MCP tools have English aliases (`sezgi key create --name k`, `sezgi key pin`, `--out`, `--sign`, `--frontend`, `--map`, `--strict`, `sezgi report`, `sezgi mirror`, `sezgi remove`, `--tool`, `--steer`, `sezgi mcp --lang en`, `sezgi observe import`, `sezgi observe scenario`, `sezgi rea install`, `sezgi switchboard link-entity`, `sezgi plan show`); most live-mode, observation and REA flags exist only in Turkish. The command line's output (help, errors, `doktor`, reports, live mode, prompts) is in Turkish or English: `--lang en` or `--lang tr` on any command, otherwise `SEZGI_LANG`, otherwise the system language (the Windows display language, or `LC_ALL` / `LC_MESSAGES` / `LANG`); Turkish when it cannot be told. In English, `sezgi help` lists the English names first and suggests English commands. JSON keys and the map, evidence store and Benlik Card that `init` writes do not depend on the language; text taken from them (for example an adapter's reason for an unmapped route) is shown as stored. See the [glossary](GLOSSARY.md).

Exit codes: `0` success; `1` the command failed (a file or folder is missing, the state does not allow it, the app could not be reached, a check such as `dogrula` found a problem); `2` the command line is wrong (a missing or invalid argument or value, an unknown flag or subcommand), with the command's usage line. Every error message says which.

## How it works

1. **Read:** every source file (TypeScript, JavaScript, Python, Java, Kotlin, Ruby, C#, Go, PHP) is parsed once with tree-sitter, in parallel on all cores. Each file's content digest is kept, so `izle` re-parses only changed files and staleness is decided by content, not by timestamps.
2. **Understand:** a framework adapter maps decorators, routers and schemas to endpoints, inputs, rules and auth. NestJS conventions (decorator names, guard patterns, prefixes) are data in [`adapters/nestjs.toml`](../adapters/nestjs.toml); the TypeScript class model, zod, the module graph, Express / Fastify / Next routing, FastAPI, Django, Flask, Spring Boot, Ktor, Rails, ASP.NET Core, the Go HTTP frameworks and Laravel are Rust.
3. **Know what is not known:** every fact carries a stamp. Facts read directly from code are `certain`; conclusions drawn from absence or naming (for example "no login guard found, so public", or table links) are `inferred`; what cannot be resolved is reported as unknown instead of being filled in. Certainty follows definitions, not names: a field is required because of its validators (not because it lacks `?`), a public marker counts only when its `SetMetadata` key is read by the login guard, a global guard counts only when it is registered in a module reachable from the root module. A negative corpus of traps where Sezgi must not claim certainty is part of the test suite.
4. **Keep the evidence:** every claim in the map is stored with its evidence in `.sezgi/kanit.json`: source kind, file and line, the file's digest, a confidence on one scale (`certain` > `observed` > `inferred` > `unknown`) and whether the list it belongs to may be incomplete. A source kind has a ceiling (shipped files at most `observed`, heuristics at most `inferred`); several weak pieces of evidence do not add up to a strong one; a contradicting piece from another source kind (code, capture, database schema, human confirmation) lowers the claim, while different values from the same kind are context and only noted; a claim whose file changed is shown as stale. `graf.json` is the same claims as nodes and edges: endpoints, tables and their columns (`field:`, with the real table and column names from `@@map` / `@map` or `__tablename__`), input fields and the validation rules on them (`rule:`), roles, modules and routers (`mod:`: the NestJS module graph, FastAPI router inclusion, Django URL configurations and DRF routers, Flask blueprints, Spring controllers, ASP.NET Core controllers and route groups, Go router groups and mounts, Laravel route files with what loads them) with the environment conditions a route is registered under (`env:`), screens, UI actions, client calls, journeys, and internal events and jobs. The MCP tools `kanit`, `bilinmeyenler` and `etki` read it. No database: plain JSON files, read into memory.
5. **Link data:** with a Prisma schema (or SQLModel / SQLAlchemy, JPA entities with Spring Data repositories, Exposed tables, ActiveRecord with `db/schema.rb`, Entity Framework Core, GORM, Eloquent models and Laravel migrations, or SQL in Express and Go handlers), each endpoint lists the tables it may read and write, followed through services.
6. **Summarize behaviour:** from the handler and the services and dependencies it calls, Sezgi reads conditional rejections with their HTTP code (`throw new ForbiddenException()`, `raise HTTPException(status_code=403)`, `res.status(404)`, `throw new ResponseStatusException(HttpStatus.NOT_FOUND)`, `orElseThrow(...)` with the code from `@ResponseStatus` or an `@ExceptionHandler`, `return NotFound()`, `abort(403)`, Django `return HttpResponseForbidden()`), object-level ownership checks (`item.owner_id != current_user.id`; a filter by a path parameter such as `delete(Item).where(Item.owner_id == user_id)` is not one), conditions that split the behaviour in two (`force ? Deleted : Trashed`), soft deletes and restore endpoints (reversibility), rows deleted indirectly by a cascade (Prisma, SQLModel / SQLAlchemy, TypeORM, JPA and Entity Framework Core schemas, and `ON DELETE CASCADE` in migration files: raw `.sql`, SQL in Kysely or TypeORM migrations, Alembic, Laravel `cascadeOnDelete()`, with table renames followed in order), and the events and jobs an operation emits or queues (`emit`, queues, `add_task`, Celery `.delay`, Spring `publishEvent`, Kafka / JMS / Rabbit sends, `@Async` calls, MediatR `Publish`, Laravel `event()` and `::dispatch()`) with their listeners (`@OnEvent`, `@OnJob`, `@Process`, `@EventPattern`, `@EventListener`, `@KafkaListener`, `@Scheduled`, `INotificationHandler<T>`; `BackgroundService` jobs; Laravel listeners and queued jobs) and what those delete. A pattern in the handler itself is `certain`; one reached through a service or a dependency, and every cascade, is `inferred`. Coverage stays open: a rejection that is not listed may still exist. `tani` shows the summary; the preview lists the service-internal rules it cannot check, so such a write waits for approval. The card carries it in `x-dna`, events and jobs in `x-nodes` and `x-relationships`.
7. **Follow calls:** a call graph over every function and method (TypeScript / JavaScript, Python, Java, Kotlin, C#, Go, PHP, Ruby). A call is linked to its target as `certain` only when the target is static and single: the same class or a parent class, a function in the same file or an imported one, a method of an injected service whose type is known (NestJS and Spring constructor injection, Spring `@Autowired` fields, ASP.NET Core registrations `AddScoped<I, C>()` found in code, FastAPI `Depends(Class)`, PHP promoted constructor parameters, Rails `before_action`). The only implementation of an interface, a class taken from the Laravel container (`app(X::class)`), a MediatR handler or a name found only once in the project is `inferred`. A call whose target the code does not tell (index access, reflection, a function passed as a parameter) is counted as unknown and gets no edge. Each call is a `CALLS` edge in the evidence store with the file and line of the call. From every endpoint Sezgi walks the graph down to the service and repository layers (at most 8 steps, 400 functions) and collects table effects (Kysely, Prisma, TypeORM, Sequelize, Mongoose, SQLAlchemy / SQLModel, Django ORM, Spring Data JPA, Exposed, EF Core, GORM, Eloquent, ActiveRecord, MyBatis XML mappers and raw SQL strings), access checks (`requireAccess` / `checkAccess`, `authorize($post)`, `Gate::allows`, `can?`, `@PreAuthorize`, `[Authorize(Policy = ...)]`) and ownership comparisons. An ownership check is only a comparison of the record's owner field with the requester's identity (`item.owner_id != current_user.id`); a uniqueness check (`existing.id != user_id`, 409) or "you cannot delete your own account" is not. `tani` shows the chain (`AlbumController.deleteAlbum → AlbumService.delete → AlbumRepository.delete`), `etki` lists the functions on it, the preview counts object-level checks as not checkable (such a write waits for approval, and so does a write on a record whose call chain could not be resolved completely), and `rapor` has a call section. File summaries are cached by content, so `izle` re-reads only changed files.
8. **Read responses:** the schema of the successful response, from FastAPI `response_model=` or the return type, NestJS `@ApiResponse` / `@ApiOkResponse` / `@ApiCreatedResponse({ type })` or the method's return type, a Django REST Framework view's serializer, Flask-Smorest `@blp.response` and `@marshal_with`, the return type of a Spring handler, the payload of a Ktor `call.respond(...)`, the Rails action's jbuilder template, serializer or `render json:` expression, ASP.NET Core `ActionResult<T>`, `Results<Ok<T>, …>`, `[ProducesResponseType]` or `.Produces<T>()`, a Laravel API Resource's `toArray()` or `response()->json([...])`, the object keys of an Express `res.json({...})`, and the value a Go handler writes with `c.JSON(200, x)` / `json.NewEncoder(w).Encode(x)` (its static type is `certain`, a `gin.H{...}` map's keys `inferred`). An explicit declaration or a type the framework enforces is `certain`; a return type in NestJS or a guess from the handler is `inferred`. It goes into the card (`x-response`) and the generated OpenAPI document (`responses`).
9. **Say what the app is for:** the README, the package manifest (description, keywords), the OpenAPI title, table and model names, path and module names and role names are counted against a dictionary of about twenty-five business domains (personal finance, monitoring and alerting, IoT, helpdesk, inventory and newsletters among them). The app's own description (README title and first paragraph, package and OpenAPI description) weighs more than table names, and table names more than path names. A domain ("photo and video library", "e-commerce", "wiki and documentation platform" …) is named only with at least two kinds of evidence and a clear lead over the next candidate; evidence from code names alone needs more, and loses to a description that names another domain; otherwise it stays `unknown` and the candidates are listed. A project template or an example app is told apart from its domain. Why the app exists is the app's own sentence, quoted with file and line; the problem it solves is the domain's description (only when the domain is known) plus a quoted sentence about its benefit from the README's descriptive part (security, configuration, architecture and other technical sections are never quoted). Users are grouped into types (anonymous visitor, signed-in user, API key / token client for operations behind a guard that reads a key or token from the request, administrator, role names) with their sign-up, login, password-reset, SSO, e-mail and 2FA flows, and operations into business capabilities ("share album", "upload photo"): a `cap:` node that its endpoints `IMPLEMENTS`. All of it is at most `inferred`: a quote is what the app says about itself, not a verified fact. Local and deterministic: no network, no language model.
10. **Report external effects and reversibility:** outgoing HTTP clients (fetch, axios, got, NestJS `HttpService`, requests, httpx, aiohttp, urllib, HttpClient, RestTemplate / WebClient / Feign, Ktor HttpClient, Guzzle / Laravel `Http`, net/http, resty, Net::HTTP / Faraday / HTTParty), queue and event publishing (Kafka, RabbitMQ, SQS / SNS, Pub/Sub, Azure Service Bus, MassTransit), e-mail (nodemailer, smtplib, Django / Laravel mail, ActionMailer, JavaMailSender) and payment and cloud SDKs (stripe, aws-sdk / boto3, @google-cloud) are found and tied to operations through the call chain. The chain is also followed over the function call graph, as deep as the graph goes: a method called on a base-class type or on a receiver whose type is unknown reaches every method of that name in the subclasses or the project (polymorphic dispatch, at most `inferred` even with one candidate), and a call that leaves the project is classified by the package it enters, an import alias included (`EmailMultiAlternatives as Message`, pycurl, urllib3, minio): outgoing (HTTP, e-mail, queue, payment, cloud, notification), internal (standard library, framework, ORM, logging, JSON, dates, validation, error tracking) or unclassified. A write whose chain has an unclassified library call, a dynamic call (reflection, a choice by index or `getattr`, `send`), too many candidates or a chain cut at the depth limit has an unknown external effect (`dis_etki: bilinmiyor`) and never goes without approval (fail-closed); for a read it is only information. A fixed address is `certain`, a target from an environment variable `inferred`, a target the code does not resolve `unknown`; the graph node is `external:<host | ortam.NAME | sdk>`. Every write gets `geri_alinabilir` (yes / partly / no / unknown) with its reason: soft delete (field, `SoftDeletes`, `paranoid`, `acts_as_paranoid`, `@DeleteDateColumn`, `gorm.DeletedAt`, inherited from a base class), a restore endpoint, a reverse action (`flag` / `unflag`, `unvote`, a DELETE on the same path after an add or a mark, `/cancel`, `/undo`; an update is never undone by a delete and a collection-wide DELETE is not the reverse of creating one record), a version or history record on update (revision tables, PaperTrail, Envers, django-simple-history, Laravel revisions, EF Core temporal tables) with a revert endpoint, a hard delete, cascades, a transaction boundary and an external effect that cannot be undone; at most `inferred`. Relative calls of a client registered with dependency injection take its registered base address (ASP.NET `AddHttpClient<T>`, NestJS `HttpModule.register`, Spring `WebClient` beans, a Ktor `HttpClient` with `defaultRequest { url(...) }`). Conditional rejections in the chain (`abort_unless`, a `throw new Error` without a status code) become preconditions and the preview does not say PASS for them. A write that reaches an external system or cannot be undone never goes without approval. A call to the base of another switchboard member is a cross-application link. `tani`, `etki`, `rapor`, the card (`x-dna.side_effects`, `reversibility`, `x-external` at the root) and Ayna show the same data.
11. **Serve:** small, source-linked answers over MCP, a coverage report and a local UI.

Database table links against an independent type-checker referee: 603/603 links on the private app, 341/341 on Cal.com, no extra links ([`kanit/SONUC-4-veri-baglari.md`](https://github.com/atabaykut/Sezgi/blob/main/kanit/SONUC-4-veri-baglari.md)).

## The Benlik Card (Draft 0.1.1)

`benlik.json` is the app's self-description in the open [Benlik Card format](https://github.com/benlik-spec/benlik-spec): operations, inputs, rules, roles, identity model and data ledger, every fact with a stamp. Draft 0.1.1 adds, as `x-` members that 0.1 readers ignore:
- **Validity:** `x-issued_at` / `x-expires_at` (default 30 days, `init --gecerlilik`). An expired card fails `sezgi dogrula`, and live mode does not write on it (reads go through with a warning) until `sezgi init` renews it. A card without an end time, or one that cannot be read, counts as expired: removing `x-expires_at` does not open writes.
- **Freshness:** `x-basis` holds the SHA-256 of every source file the operations rely on; staleness is computed from it, never written by hand.
- **Evidence:** `x-evidence` (one digest per evidence record) and `x-evidence_root` (their Merkle root); the records themselves are in `benlik-evidence.json`, signed with the same key in its own context. The card carries no values, paths or contents of the evidence.
- **Behaviour summary:** `operation.x-dna` (login, failure conditions including service-internal ones, data effect with `indirect` cascade deletes, two-way conditions in `branches`, reversibility with its reason, outgoing calls in `side_effects`, the transaction boundary, coverage, evidence references).
- **Response schema:** `operation.x-response` (type, array, status, fields, stamp, where it was read).
- **User journeys:** `x-journeys` (ordered screen and UI-action steps ending in an operation; `inferred` from code, `observed` when seen at run time).
- **Events and jobs:** `x-nodes` (internal events and jobs with their listeners; they are not operations) and `x-relationships` (an operation or node `triggers` an event or job, a job `writes` a table, a cascade `may_affect` one; all `inferred`).
- **Without source code:** a card written by `sezgi kesfet` has no operations and carries `x-sourceless`, `x-app_node`, `x-preview` (never passes), `x-capabilities`, `x-screens` and `x-webmcp`, each item requiring approval.
- **Meaning:** `app.x-meaning` (domain with its evidence, kind, quoted purpose, problem, user types, sign-up and login flows, business capabilities with their endpoints; every stamp at most `inferred`, `unknown` when the evidence is not enough) and `app.description` (the app's own sentence, `inferred`, with file and line).
- **Changes:** `changes` lists added and removed operations and breaking changes since the previous card, computed without commits.

Validators for the card (schema, rules, evidence, signature) are published as `benlik` on npm, PyPI and crates.io.

## Live mode

By default Sezgi only maps and previews (`gozlem`, observe). The shortest way is one command: it asks for the target, confirms it is a test copy, then the mode, the human session and the first token. Each step is a separate gate and the defaults are the most restrictive (read mode, read-only permission):

```sh
sezgi live setup    # = sezgi canli kur; in scripts: --hedef <url> --test-kopyasi --mod yazma --izin "book.*:yaz"
sezgi live          # status: mode, target, session, tokens, pending approvals, log chain and the next step
```

The same steps one by one:

```sh
sezgi hedef http://127.0.0.1:3000 --test-kopyasi   # the test copy; writes never go anywhere else
sezgi mod okuma                                      # forward reads; `sezgi mod yazma` also forwards permitted writes
sezgi token olustur --ad "design team" --izin kitap.*:yaz --izin kitap.sil:yikici   # shown once
sezgi oturum ac --rol editor                         # paste your own session token for the app; declare your role
```

A remote target must be `https://`; plain `http://` is accepted only on this computer. Tokens are closed by default, expire (`--sure <days>`) and can be revoked (`sezgi token listele`, `sezgi token iptal <name>`); only their hash is stored. A pattern that opens writes on everything (`*:yaz`) needs explicit confirmation (`--tum-islemler`). A pattern that matches no operation of the map (usually a typo, `kitp.*:yaz`) is reported with the closest pattern; `--kesin` makes it an error and no token is made. Without a terminal, `sezgi oturum ac` reads your session value as one line from standard input (`printf '%s\n' "$SESSION" | sezgi oturum ac --rol editor`).

Tokens can also be created in Ayna: the **İzinler ve token** (permissions) tab lists every operation by module with what it does (the summary from the code; without one, a description read from the function name and stamped "inferred"), login, roles and the tables it touches. Everything starts unchecked; the checked operations become the token, shown once with the connection line. No wildcards: operations added later are not opened automatically.

**Operation tools:** an agent connected with a token sees every operation the token allows as its own tool (e.g. `kitap_olustur`). The name comes from the operation, the description from the summary in the code, the input schema from the map's fields, types and rules. Deletes carry MCP's destructive hint, reads the read-only hint. Every call passes the same gates as `cagir`; in observe mode it only previews. Descriptions from code are reduced to plain text, truncated and marked as data, not instructions. The tool list stays fixed for the connection. Above 40 allowed operations they are not listed one by one and the agent uses `ara` → `tani` → `cagir` (threshold: `SEZGI_ISLEM_ESIGI`, 0 turns it off). Ayna shows the tools the agent will see when it creates a token.

**Visibility follows the token:** an agent connected with a token sees only the operations that token can call. `ara`, `tani`, `onizle`, `cagir` and `kimsin` hide the others; `kimsin` says how many are hidden. An unknown, revoked or expired token shows nothing. Without a token the whole map is visible to the read tools, and nothing is forwarded.

**Every request** sent through `cagir` (English: `call`, with `SEZGI_TOKEN` set) or an operation tool passes these gates; a request that fails one is not sent:
- **Mode** (`okuma` forwards reads, `yazma` also writes) and the **token's permission** for this operation and level (read, write, destructive).
- **Target:** writes go only to the declared test copy, or to a target where a human opened writes on real data (below).
- **Fresh map:** a write is refused when a source file of the map changed since it was built (when the map is the app's own `.sezgi` folder, which is the default).
- **Valid card:** a write is refused when the Benlik Card has expired, has no end time or cannot be read.
- **Map matches the card:** approval decisions are read from the map, so a write (and an approval) is refused when the map on disk does not match the card written with it (`x-map_digest`, the canonical SHA-256 of `kapilar.json`) or the operation in memory differs from the map on disk. With a signed card the signature and the key's trust are checked too, and once a key has been pinned or seen for the application an unsigned card is refused; with an unsigned card the binding is only a consistency check.
- **Preview:** a request the preview rejects is not sent. When several operations share one address, the `islem` (`operation`) argument must say which.
- **Human session:** no human, no write. The request goes with the user's own credentials, so the app's own authorization decides: effective permission = user's permission ∩ token.
- **Duplicate protection:** the same write is not made twice within 10 minutes.
- **Log:** a request that cannot be logged is not sent.

**When a human must approve.** A write goes without approval only if all of these hold; otherwise it waits for `sezgi onay ver <id>`, which the human runs with their own session:
1. it is not destructive;
2. the operation's evidence is `certain` (inputs, rules and the login decision read from code) and no evidence contradicts it (for example a recorded request that the app accepted although the code's schema rejects it; `tani` marks such an operation as contradicted);
3. the preview passed in a closed world: every known rule was checked (a rule it could not check is not a pass);
4. if the operation needs a role, the human holds it as a **verified** role: declared by the human in a terminal (`sezgi oturum ac --rol <role>`; a declaration piped in without a terminal, as a script or an agent would make it, is not counted; with a system anchor in place, roles from any source count only when the human confirms them with the human password, which signs them, so a role typed into a pseudo-terminal or written into the session file is not counted), a claim in an OIDC ID token whose signature was verified (`--rol-claim`), or read from the app's own "current user" endpoint with the human's session (`--rol-ucu <path> [--rol-yolu <json.path>]`). A role the agent claims is never trusted and is dropped before the preview;
5. the token was not created with `--onay hepsi` (approval for every write);
6. the map is fresh and the card valid (above).

Approving is bound to what was asked: `sezgi onay goster <id>` shows the method, address and body with a digest, and every request, a bodyless delete included, is approved against it (an explicit "evet" in a terminal, `sezgi onay ver <id> --ozet <first 8 characters>` when no terminal is available). At approval time the token, its permission, duplicate protection, freshness, card validity, mode and target are checked again; two concurrent approvals send one request. `onay_durumu` lets the agent ask how its request ended.

**Writes on real data (experimental).** Live mode writes to a test copy unless a human opens writes on the app's real data, and then under stricter gates than on a test copy:
- **Human key (system anchor):** proof that a human is there is a password only the human knows. An administrator sets it once: `sudo sezgi insan kur --sistem` (Windows: `sezgi insan kur --sistem` in a terminal run as administrator). Sezgi derives a signing key from the password (PBKDF2-HMAC-SHA256, 600,000 rounds, random salt, then Ed25519) and writes only the salt and the public key to a file the user cannot change: `/etc/sezgi/insan-<uid>.json` owned by root and not writable by group or others, or `C:\ProgramData\sezgi\insan-<user>.json` owned by Administrators or SYSTEM and not writable by the process reading it, in a folder owned by Administrators or SYSTEM whose access list lets no one else change it. On Windows the setup takes the folder over for Administrators if someone else owns it (for example a user who created `C:\ProgramData\sezgi` first), cuts inherited permissions and writes an explicit access list on the folder and the file: Administrators and SYSTEM full control, Users read only; if it cannot, it stops with the reason and the `takeown` command to run. `--kullanici` takes a uid or, on Linux and macOS, a user name from `/etc/passwd`. The password and the private key are never stored. A file in the user's own folders is never an anchor, because an agent could delete it and set its own password. Without an anchor, writes on real data stay off. `sezgi insan` shows the anchor; changing the password needs the current one (or an administrator deleting the file). `sezgi canli` and `sezgi doktor` show it too.
- **Opening:** `sezgi hedef <url> --gercek-veri` works only in a terminal, after the human types the app's name and then the human password; without a terminal or an anchor it is refused. It cannot be combined with `--test-kopyasi`. The setting is kept and signed with the human key; `sezgi hedef`, `sezgi mod`, `sezgi canli` and `sezgi doktor` show it as `GERÇEK VERİ` (real data). `sezgi hedef <url>` without a flag turns it off.
- **Signed records, fail-closed:** the target record (address, real data or test copy, addresses once opened for real data, hourly limit) and every real-data token are signed with the human key and checked against the anchor before every write and at approval. If someone edits `ayar.json` or `tokenler.json` (another server, a higher limit, real data relabelled as a test copy, a token marked for real data), the signature fails and writes there stay off, with the reason shown by `sezgi hedef` and `sezgi doktor`, until the human opens it again with the password.
- **Protection boundary:** an agent with shell access under the same user account can open a pseudo-terminal (for example with `script`) and edit Sezgi's files, but without the password it cannot open real data, make a real-data token, approve a request or re-sign an edited record, and it cannot change the anchor. The password does not help when the agent learns it (a keylogger, the human pasting it into the agent's terminal or a file), when the agent runs as administrator or root, or when it reads the human session that Sezgi keeps for the app (OS keychain or a user-only file) and calls the app directly, bypassing Sezgi; run the agent as a separate user to close those. When Sezgi sees a pseudo-terminal or a known coding agent among its parent processes or in the environment, it prints a warning; no warning does not prove that a human is there.
- **Tokens:** only a token made in a terminal with `sezgi token olustur ... --gercek-veri`, an explicit "evet" and the human password may write on real data; older tokens (and tokens made in Ayna) only read there.
- **No automatic writes:** every write and destructive request waits for approval, whatever the rules above say. The MCP answer, `onay_durumu` and `sezgi onay goster` mark it `GERÇEK VERİ`.
- **Approval only in a terminal, with the password:** `sezgi onay ver <id>` asks for an explicit "evet" (for a destructive request the human types the method and path, `DELETE /api/books/7`) and then the human password. `--ozet` is refused on real data. The log line records `insan_kaniti: parola` and the anchor's fingerprint.
- **Checked before the request is queued and again at approval:** the Benlik Card is signed, its signature is valid, its key is pinned for the application (`sezgi anahtar sabitle`; a key that is merely consistent with the one seen before is not enough), it contains the operation and it has not expired; the map is the app's own `.sezgi` folder and is fresh; the preview checked every known rule. Otherwise the request is refused with the reason.
- **Rate limit:** at most 20 real-data writes per hour (`sezgi hedef --saatlik-yazma <1-200>`, terminal only, with the human password).
- **Log:** every real-data write is logged with `gercek_veri: true`; `sezgi kayit` marks it.
- **No silent downgrade:** an address once opened for real data is remembered, and the same server written differently (`localhost`, `127.0.0.1` or another loopback address, a default port written out, `http` or `https`, a path, a trailing `/`, letter case) counts as the same address; declaring it a test copy again (which would drop these gates) also works only in a terminal, after the human types the app's name and the human password. With an anchor in place, declaring any address a test copy needs the password too, and the declaration is signed like the real-data target (an agent cannot relabel the real server as a test copy). A request queued on real data keeps the real-data rules at approval even if the target has changed since.
- **Undo:** the approval text shows the operation's reversibility verdict (yes / partly / no / unknown) and its reason (from the source, at most inferred). A write that reaches an external system (outgoing HTTP write, e-mail, payment, queue, cloud) or cannot be undone always waits for approval, and so does a write that changes credentials (a password, token, key or two-factor setting) whose reversibility is not shown. Sezgi takes no backup and cannot undo a write: back up the app before a change that cannot be undone.
- Change plans across apps follow the same rules: a step on real data needs a real-data token and is approved only in a terminal, with the human password.

Each request is written to a hash-chained log without parameter values (`sezgi kayit`, `sezgi kayit --dogrula`, `sezgi kayit --json` for an auditor). The log is encrypted at rest (ChaCha20-Poly1305, one key per project); so are the bodies and arguments of requests waiting for approval and the responses kept by the experience memory.

Data ledger: `sezgi defter` shows what Sezgi keeps: the code-derived map; the operational log; and customer data, which is written only encrypted and only where a feature needs it (requests waiting for approval; responses, if you turn the experience memory on). The log is kept 30 days by default (`sezgi defter --saklama 7..365`) and deleted when the period ends, regardless of disk space. `sezgi unut --kisi <id>` closes a deletion request (KVKK / GDPR): the person's id is removed from every log line while the chain still verifies, because the person enters the chain only as a hash; `sezgi unut --hepsi` removes all customer data. The Benlik Card's `data_ledger` states this. `sezgi teshis ac` turns on an optional local diagnostics log with counters only (calls per tool, errors, durations, memory where measurable); it holds no code, queries, addresses or ids and is never sent anywhere.

## Run-time observation

Code says what an application should do; an observation records what it did (`sezgi gozlem`, not to be confused with observe mode, `sezgi mod gozlem`). There are three sources and one projection: only the shape of a request is kept, that is the method, the path template (number-, uuid- and value-like segments become `:param`), the status code, the top-level field names and JSON types of the request and response bodies, and the query parameter names. No values are kept: no bodies, query values, headers (`Authorization` included), cookies, tokens or e-mail addresses; keys that do not look like names (e-mail addresses, tokens, ids, long or random-looking strings) are only counted. Observations go to `.sezgi/gozlem.json`, the evidence store is rebuilt with them at once, and they enter the card on the next `sezgi init`. `tani` shows whether an endpoint was observed, with which status codes and response fields.

- **Network capture:** `sezgi gozlem al <file.har>` reads a HAR file saved from the browser's developer tools, as a stream; only its SHA-256 is kept, not the file. Static files and other origins (analytics, CDN) are skipped. A request that matches an endpoint of the map is `NETWORK_CAPTURE` evidence, at most `observed`: the endpoint works (2xx/3xx), its error statuses (4xx/5xx), its response shape. The body of a successful request is compared with the input schema from code and the response with the response schema: an accepted request without a required field, a different type or a response field the code does not declare is a contradiction, and the claim drops to at most `inferred`. An observed endpoint that is not in the map is listed among the unknowns. `--isaretler <json>` (`[{"ad": …, "zaman": …}]`) links time marks to the requests that follow within 2 seconds; such a UI link is only `inferred`, because a HAR carries no step information.
- **Live mode:** every request live mode actually sends (`cagir`, an operation tool, `sezgi onay ver`, a plan step) is recorded the same way; the human and the token do not enter it.
- **Browser scenario:** `sezgi gozlem senaryo <scenario.json> --cdp <http://127.0.0.1:port> --onayla --yalitim konteyner|vm|yok --calistir --sahibiyim` runs a scenario you wrote (steps `git`, `tikla`, `doldur`, `bas`, `bekle`, `bekle_ms`; elements found by role and accessible name, by `test_id` or by CSS selector; each step times out, 15 s by default) through REA's `capture-browser-scenario`, in a browser you opened on this computer with a debugging port. The tool changes the target and runs the page's code, so it is in the dynamic class: besides the flags it asks for `evet` in a terminal. The start address, every `git` address and the CDP address must be on this computer (loopback). Values to fill are never written in the scenario: each comes from an environment variable (`{"ortam": "NAME"}`) or a file (`{"dosya": "path"}`) and reaches REA only as a secret in its own process environment, never in the scenario, the command line or the evidence. REA links every request to the step that started it; Sezgi keeps the method, path template, status code and step. A UI action → endpoint link and the journey's UI step become `BROWSER_OBSERVATION` evidence, `observed` (`inferred` with `--yalitim yok`), and the request order makes the journey `observed`.

Observation evidence rests on the source file of the matched endpoint: when that file changes, the observation becomes stale. Observations cannot be added to a map built by `sezgi kesfet` in 0.1.

## Switchboard: several applications

One Sezgi can serve several applications. `sezgi santral ekle <map-dir> --ad <name>` registers an app; `sezgi santral ekle --istemci <dir> --ad <name>` registers a client without a map (a web front end or a mobile app); `sezgi santral cikar <name>` removes one. `sezgi mcp --santral` serves all of them: `kimsin` and `ara` cover every app, and `tani`, `onizle` and `cagir` go to the right one (`"name: METHOD /path"`, the `uygulama` argument, or the only app that has the endpoint). `SEZGI_TOKEN` may hold several tokens separated by commas, one per app.

`sezgi santral baglar` finds cross-links: which client or app file calls which endpoint of another app. A link is `kesin` when the address matches exactly (a variable in place of a path parameter included) and `yorum` when the global prefix lives in the client's base URL or a literal value meets a parameter. Server-side route definitions and decorators are not counted as calls. An app whose source folder is unknown is reported as "not searched", separately from "searched, 0 links". The MCP tool `baglar` answers who calls an endpoint.

The same real-world thing often lives in several apps: a reservation system's guest is the transfer system's passenger. `sezgi santral bagla-varlik reservations:Guest.passportNo transfers:Passenger.passportNo` records that mapping in your config folder (`santral-varliklar.json`; schema level only: no record values are stored; `--anahtar <name>` adds a note naming the key). A human definition counts as `USER_CONFIRMED`: without source-code or API-schema evidence it is at most `observed`, and it goes stale when either schema file changes. When one app's code calls the other with that field (`GET /reservations/:no` with `${transfer.reservationRef}`), the mapping is backed by source code and becomes certain if the data flow is unambiguous. `sezgi santral varlik-gozle A:Entity.field=B:Entity.field --ornek 50` asks for your confirmation (`--evet` where there is no terminal), then reads both test copies with your own session through each table's parameterless `GET` operation (each app needs `okuma` or `yazma` mode, a target declared as a test copy and your session), matches values in memory and keeps only counts and the match rate (`observed`); a rate below 0.5 counts as a contradiction. `sezgi santral varliklar` lists mappings with their confidence and suggestions from name, type and external-id similarity, which are never more than `inferred`. Over MCP, `varliklar` shows them and `etki` crosses app boundaries: changing an operation may affect the mapped entity in another app (`MAY_AFFECT`, never certain) and the operations that use it.

The MCP tool `plan` lets an assistant propose one change across several apps (it needs a token). It only records the plan, in your config folder (`santral-planlar/`, owner-only; step bodies and arguments encrypted with each app's own key): nothing runs. `sezgi plan listele` lists plans, `sezgi plan reddet <id>` rejects one. You review every step with `sezgi plan goster <id>` (app, operation, body, mapped entities it may affect, business rules from the card) and approve steps in order with `sezgi plan onayla <id> --adim <n> --ozet <digest>`. Each step goes through the same gates as any live-mode write: the token's permissions, your own session and verified role, a fresh map, write mode on a test copy (or on real data, with its stricter rules: a real-data token and approval only in a terminal), a preview against today's map and the content digest you saw. The assistant's role claims or plan arguments cannot open a gate.

Not yet: calling an application's internal functions through a connector installed in it, and an agent driving the UI in a browser (`sezgi gozlem senaryo` only runs a scenario a human wrote, to observe it).

## Compute and GPU waste

Sezgi does not make a model faster; it removes waste around it:
- **The same job twice:** with the experience memory on (`sezgi hafiza ac`, off by default), a side-effect-free read that was already answered comes from memory in milliseconds instead of reaching the app and its GPU. Only GET/HEAD operations without known table writes and successful (2xx) answers; never writes; never responses containing e-mail addresses; answers fetched with the human's session only with `--oturumlu`; isolated per token; invalidated when the map is rebuilt; retention and disk limit apply.
- **A bad request failing after minutes:** in live mode the preview rejects it before it reaches the app.
- **The agent scanning code:** it asks Sezgi instead (`sezgi olc` measures the difference on your app).
- **A big model for a small job, a restart from scratch:** the `tani` card lists lighter options (values such as `fast`, `draft`, `turbo`), fields that drive cost (`model`, `steps`, `quality`) and resume endpoints. These hints come from parts of names and values and are marked as such; the user decides the quality. On Fooocus-API (pre-registered) they found 0/7 cost fields before name parts were used and 7/7 after (not held out); on apps without a GPU they also produce wrong hints (`kanit/SONUC-14`).

## 0.1 targets

All eight 0.1 measurement targets were met on the public apps (one machine, earlier build): startup with a ready map about 10 ms (target < 100 ms), card lookup and routing p95 under 1 ms (Immich p95 0.92 ms, Cal.com p95 0.68 ms; target < 5 ms), validation rules extracted as `certain` 265/265 on Cal.com (target ≥ 60%), wrong links 0. The "~100 thousand lines < 15 s" target was measured later on the Twenty server: **981,837 lines in 3,647 ms, peak memory 273 MB** ([`kanit/SONUC-13-olcek.md`](https://github.com/atabaykut/Sezgi/blob/main/kanit/SONUC-13-olcek.md)). Table and limits: [`kanit/SONUC-8-01-hedefleri.md`](https://github.com/atabaykut/Sezgi/blob/main/kanit/SONUC-8-01-hedefleri.md).

## Known limitations

- **Live mode on real data** is experimental. It needs a system anchor set up by an administrator; it is opened only in a terminal and every write there is approved in a terminal with the human password, which an agent with shell access under the same user account does not know; it does not stop a program that learns the password, runs as administrator, or reads the stored session and calls the app directly (see *Writes on real data* and SECURITY.md); Sezgi has not had an independent security audit yet. Certificates are verified against the OS trust store (a self-signed test copy's CA can be added with `SEZGI_CA_DOSYASI=<pem>`; verification cannot be turned off). The human session is kept in the OS keychain on Windows (Credential Manager) and macOS (Keychain); on Linux, and where no keychain is available, in a file only the user can read. The human session can also come from the app's identity provider: `sezgi oturum ac --oidc <issuer> --istemci <client_id>` uses the OIDC device flow (RFC 8628: the person approves in their own browser, Sezgi never sees the password), renews the access token with the refresh token within the session limit, and with `--hedef-kitle <audience>` exchanges it for a narrower token valid only for the app (RFC 8693; if the provider refuses, no session is opened). The provider must be `https://` (a provider on this computer may be `http://`). The log key is kept like the session: losing it makes the old log unreadable, and Sezgi then refuses to send requests rather than start a new chain. Responses are passed to the agent unmasked.

Reported rather than hidden. Where a limitation can make a fact wrong, Sezgi stamps it `inferred` or `unknown`; the items marked **(not stamped)** can produce a wrong value without a weaker stamp.

- **Guards are recognized by name.** A guard whose name contains `jwt` or `auth` counts as a login guard; Passport strategy guards (`AuthGuard('…')`) count only for session strategies (`jwt`, `bearer`, `api-key`, `session`, `basic`), others are treated as unrecognized. A misleadingly named guard gives a wrong decision with a certain stamp **(not stamped)**.
- **Composed decorators:** guards, roles and markers applied through a project decorator (`applyDecorators(UseGuards(…))`, nested up to 3 levels) are followed; conditionally applied ones are not (`inferred`). Public markers built with `Reflector.createDecorator` are not traced (`inferred`).
- **Roles:** decorators whose name ends in `Roles` are read. When both the controller and the method declare roles (merge or override depends on the app's guard), or a role value cannot be resolved (for example a numeric enum), the role decision is `inferred` and the preview neither passes nor rejects on roles.
- **Required flags:** a field is certain only when its validators decide it. Custom decorators are followed through their definitions; a conditional `IsOptional` or an untraceable decorator makes the flag uncertain (`inferred`).
- **Paths:** `setGlobalPrefix` is read; `enableVersioning` URI prefixes, `RouterModule` prefixes and prefix `exclude` lists are not applied, and a path built from a constant that cannot be resolved keeps the identifier text **(not stamped)**.
- **Preview:** custom validators, rules chained on zod array elements (`z.string().min(2).array()`) and union types are listed as "could not be checked", never guessed.
- **Call graph and table links:** the call graph is static. Dependency-injection bindings made at run time, dynamic dispatch, wrappers registered at run time and calls inside libraries are not followed; a chain is followed at most 8 steps and 400 functions (a deeper chain is marked partial). An interface-typed injection is followed to the class registered in code (`certain`) or to the only implementation in the project (`inferred`), never to several. MyBatis XML mappers are read (the statement's SQL gives the tables); stored procedures are not. Table links and access checks found through a chain are `inferred`.
- **ASP.NET Core:** routes built at run time by libraries (Carter, FastEndpoints, reflection over endpoint classes) are not read; a MediatR request wrapped in a generic envelope (`IdentifiedCommand<T>`) is not followed to the inner handler, so its table links are missing (not marked incomplete); an untyped `Ok(x)` / `IActionResult` response has no schema; a file using the newest C# syntax the grammar does not know yet (collection expressions inside initializers) is read partially and listed in `rapor`.
- **Laravel:** routes registered from values the adapter cannot evaluate (configuration, the database, a loop over a computed list) are left out or, inside a loop whose list is unknown, marked conditional; `Route::fallback` and redirects are not listed as operations. A `min` / `max` rule is converted only when the field's type rule says whether it measures length, value or count. Closure middleware and middleware whose alias cannot be resolved are unrecognized guards (`inferred`).
- **Kotlin:** the Kotlin grammar (`tree-sitter-kotlin-ng` 1.1.0) misreads a few constructs (for example a one-line `companion object { val x = 1 }` followed later by an `object` declaration); such files are reported as partially read and the class headers and members inside the unread region are recovered. Ktor routes built at run time (from data or configuration in a loop) and the logic inside application-level plugins (`createApplicationPlugin`) are not read; Spring WebFlux functional routes (`coRouter { }`) are not read.
- **Front-end links:** React, Next.js, Preact, Vue, Svelte, Angular, Remix / React Router v7 and Solid front ends are read; other frameworks are not. A screen's login requirement from a guard and a server function's own operation are not known for certain: guards are `inferred`, and a `"use server"` function is followed into its calls but is not an endpoint itself. Screen changes and journeys are always `inferred` from code.
- **Meaning is a dictionary, not understanding:** domains come from a fixed list of about twenty-five; an app outside it, or with too little evidence, is `unknown`. Capability names come from paths, function names and HTTP methods, so an oddly named endpoint gets an odd name (`inferred`). Search and task plans translate Turkish and English through the same dictionary; a word it does not know is matched as written, and a request for something the app has no endpoint for finds nothing rather than a verb-only match. A task plan pairs each step's verb with its object: the object is matched to a resource (a step without one, such as "favorite it", takes the fitting thing from the step before), the verb to the operation's action. A read verb (list, show, find, check) never picks a write, an operation whose action does not fit the verb is not picked, and a step with no fitting operation says so; a near fit (update or delete for "close") is labelled as the closest. The plan is ordered by rule (reads, then writes, deletes last) and never runs.
- **Behaviour summary:** rejections, ownership checks and two-way conditions are read from recognized patterns; coverage is always open, so a rejection that is not listed may still exist. Cascades are read from schemas and migration files, never from a running database (`inferred`).
- **Run-time observation:** only the shape of requests is kept, so an observation cannot tell which values a rule accepted. A HAR file carries no UI steps: a time mark links a step to a request only as `inferred`. Observations cannot be added to a map built by `kesfet`.
- **Without source code:** `kesfet` reads identities, manifests, schemas and package contents; behaviour only through REA (decompiled summaries, always `inferred`; process observation, `inferred` without isolation). Process observation is not supported on Windows (on macOS REA needs the Xcode Command Line Tools for it) and firmware regions only on Linux. No write to such an app goes without human approval.
- **Signature trust:** a key file shipped next to the card proves integrity, not identity. A card is shown as trusted (green in Ayna, "güvenilir" in `sezgi dogrula`) only when its key was pinned with `sezgi key pin`. Without a pin, `sezgi dogrula` remembers the first key it sees per application and warns when it changes (trust on first use does not protect the first encounter).
- **Signing keys on Windows** are protected by the inherited permissions of `%APPDATA%`; Sezgi sets no explicit ACL.
- **macOS:** the binaries are signed only ad hoc, not notarized. Installed through npm they run as they are; a release archive downloaded with a browser is quarantined by Gatekeeper (`xattr -d com.apple.quarantine sezgi`). After an update the Keychain may ask once whether the new binary may read Sezgi's entries (session and log key); if access is denied, the existing log is not continued with a new key and requests are refused until the Keychain can be read. The configuration directory is `~/.config/sezgi` (or `$XDG_CONFIG_HOME/sezgi`), as on Linux.
