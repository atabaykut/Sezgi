# Changelog

## 0.1.0 (not yet published)

The first release. Because nothing was published before it, this entry describes what 0.1.0 does rather than what changed; problems found and fixed during development are folded into the description of the behaviour (in particular under **Security model**), and the public evidence for the numbers is in `kanit/`.

### Mapping an application
- `sezgi init [app]` reads an application's code once (tree-sitter, in parallel on all cores) and writes the map to `<app>/.sezgi` (git-ignored) or `--cikti <dir>`: `kapilar.json` (endpoints, inputs, validation rules, login and role requirements, database tables), the Benlik Card (`benlik.json`, `benlik-evidence.json`), the app's OpenAPI 3.1 document (`openapi.json`), the evidence store and graph (`kanit.json`, `graf.json`) and, when a front end is found, `web-baglari.json`. It never writes into the application. `--deneme` / `--dry-run` explains what would be written. The output is at most 12 lines and ends with the next steps (`sezgi bagla`, `sezgi ayna`, `sezgi izle`).
- **TypeScript + NestJS** (quality level 2): class-validator and zod DTOs including mapped types (`PartialType`, `PickType`, `OmitType`, `IntersectionType`, nested), enums and constants, global prefix, custom and composed decorators (up to 3 levels), role decorators, API versions, deprecated endpoints, the module graph (global guards count only when registered in a module reachable from the root), monorepo workspace packages, nested objects and union bodies. NestJS conventions are data in `adapters/nestjs.toml`.
- **JavaScript / TypeScript + Express, Fastify, Next.js** (quality level 2): routes and mounts across modules, Next.js `app/**/route.ts` files, auth and roles from middleware (including Next.js `middleware.ts` / `proxy.ts` with matchers), zod, Joi and Fastify JSON Schema inputs, inputs read from usage (inferred), SQL and Prisma table links (inferred).
- **Python + FastAPI** (quality level 2): routes, routers and prefixes (including factories and helpers), auth from the dependency chain (certain only when a security scheme is reached; `auto_error=False` is never certain; a dependency that takes a key or token as a `Header` / `Cookie` / `Query` parameter and raises 401 / 403 requires login, inferred), Pydantic / SQLModel bodies, parameters of every kind, SQLModel / SQLAlchemy table links (inferred).
- **Python + Django** (quality level 1, Django REST Framework included): routes from `ROOT_URLCONF` through `include(...)` (`path` converters as typed parameters, `re_path` / `url` named groups, `urlpatterns +=` under conditions), DRF routers with ViewSet actions and `@action`, function and class views with their HTTP methods (`http_method_names`, generic views, `@api_view`, `@require_http_methods`); auth and roles from DRF permission classes (view, `@action`, settings `DEFAULT_PERMISSION_CLASSES`, `&` / `|`) and Django decorators and mixins, certain only for known markers, unknown for `get_permissions`; a project decorator that reads an API key or token from the request and answers 401 / 403 requires login (inferred); a function view's methods from `require_POST` / `require_GET` / `require_http_methods`, `api_view`, a project decorator that answers 405 for other methods and a leading `request.method` guard; serializer and form bodies and responses including envelopes; Django model table links, `on_delete=CASCADE` from models and migrations, and signal receivers as events (inferred).
- **Python + Flask** (quality level 1): `@route` and method shortcuts, Blueprint registration through factories and helpers (`url_prefix` at registration replaces the blueprint's), nested blueprints, `MethodView` / `add_url_rule`, Flask-RESTful, Flask-Smorest and Flask-RESTX; Flask-Login, Flask-JWT-Extended, Flask-HTTPAuth and Flask-Security decorators (certain), project decorators and `before_request` hooks, including one that reads a key or token from the request headers and answers 401 / 403 (inferred); marshmallow, Pydantic, reqparse and RESTX bodies, the keys a handler reads; Flask-SQLAlchemy table links and cascades (inferred).

Maven and Gradle projects; Kotlin sources are not read.

Route counts checked against a hand count on Koel and BookStack.
- **Operation ids:** a NestJS `operationIdFactory` built from controller and method names, and FastAPI ids built from `include_router` / `APIRouter` / decorator tags, are resolved, so operations keep the ids the app's own OpenAPI uses. Express handlers wrapped in `asyncHandler` (`catchAsync`, `wrapAsync`) are read like plain handlers.
- **Stamps:** every fact is `certain` (read from a definition), `inferred` (from absence or naming) or reported as unknown; certainty follows definitions, not names (a field is required because of its validators; a public marker counts only when the login guard reads its key).
- **Database table links:** Prisma, followed from the handler through services, helpers, inherited methods and transactions (Cal.com 341/341 against a type-checker referee).
- **Front-end links:** a React, Next.js, Preact, Vue, Svelte (SvelteKit), Angular, Remix / React Router v7 (framework mode) or Solid (SolidStart) front end in the app, beside or below it (inside the same git repository), or given with `--on-yuz <dir>` (`--frontend`), is linked screen → UI action → client call (generated OpenAPI client including oazapfts and clients in a workspace package of the same repository, axios, fetch, TanStack Query, RTK Query, SWR) → endpoint. A call is `certain` only on an unambiguous match. Screen changes (`navigate`, `router.push`, `<Link>`, `redirect` and similar) become screen-to-screen links, always inferred. Vue and Svelte templates are read (events and links), not only their `<script>` blocks. Angular: `Routes` arrays with lazy `loadChildren` / `loadComponent`, `templateUrl` and inline templates (`(click)`, `(ngSubmit)`, `routerLink`), components used by selector, `HttpClient` services injected through the constructor or `inject()`, base URLs from `environment`. Remix / React Router v7: `app/routes` file routes and `app/routes.ts`, `loader` / `action`, `<Form>`, `useFetcher`, `useSubmit`. Solid: `@solidjs/router` and SolidStart file routes, `createResource` / `createAsync`, `query` / `action` wrappers, `"use server"` functions. Screen guards (Angular `canActivate`, Vue `meta.requiresAuth`) give a screen an inferred login requirement and a `REQUIRES_PERMISSION` edge to `guard:web/<name>`. An app that depends on a back-end framework is never its own front end, and a front end found automatically that calls no API is left out.
- **User journeys:** the steps that lead to an operation (`/login › Log In → /items › Save → POST /api/v1/items/`), with the login screen and action first when the operation needs login and the screens in between. At most inferred from code; observed when the request sequence is seen at run time. `tani` and `etki` show them; the card carries them as `x-journeys`.
- **Behaviour summary:** for each operation, the conditional rejections with their HTTP code in the handler and in the services and dependencies it calls, object-level ownership checks, conditions that split the behaviour in two, soft deletes and restore endpoints, rows deleted indirectly by a cascade (from Prisma, SQLModel / SQLAlchemy, TypeORM and Entity Framework Core schemas and from migration files: raw SQL, Kysely and TypeORM migrations, Alembic) and the events and jobs it emits or queues with their listeners. Certain only for a pattern in the handler itself; coverage always open. `tani` shows it, the preview lists service-internal rules it cannot check (so such a write waits for approval), and the card carries it in `x-dna`, `x-nodes` and `x-relationships`.
- **Response schemas:** the successful response from FastAPI `response_model` or the return type, NestJS `@ApiResponse` family or the return type, Rails jbuilder templates, serializers and `render json:`, ASP.NET Core `ActionResult<T>` / `[ProducesResponseType]`, Express `res.json({...})` and Go `c.JSON` / `json.NewEncoder(w).Encode`; certain only for an explicit declaration or a type the framework enforces. In the card (`x-response`) and the generated OpenAPI document (`responses`).
- **Without source code:** `sezgi kesfet <folder|file>` (`discover`) inspects an application shipped without source, running nothing and without network access: Windows `.exe`/`.dll` and ELF identity, Android APK manifests, SQLite schemas (a foreign key declared in the schema is `observed` with its columns and `ON DELETE` / `ON UPDATE` actions; `NOT NULL`, `UNIQUE` and `CHECK` constraints are shown with the table) and Electron packages (`app.asar`: package identity, the IPC chain from a front-end call through the bridge to the main-process handler, window settings, the front end's network calls, fuses), read by Sezgi itself (no Node.js, no SQLite library). `--rea` adds .NET members, signatures and call targets from REA (`rea-agents` 6.7.0; Node.js 22.19+, 24.11+ or 26+) whose version, integrity and tool table are pinned; otherwise the bridge stays closed and says why (`sezgi doktor --rea`). `sezgi rea kur` installs REA into a private folder in Sezgi's configuration directory: it shows the package, version, source, integrity and target first, needs `evet` typed in a terminal, runs `npm ci --ignore-scripts` against a lockfile shipped inside Sezgi (the whole dependency tree pinned by sha512), then runs the bridge's pinning checks and deletes the folder if npm fails or a check does not match. `sezgi rea durum` and `sezgi rea kaldir` show and remove it; the bridge looks in `SEZGI_REA`, then that folder, then `PATH`, and `doktor --rea` and `kesfet` suggest `sezgi rea kur` when REA is missing. Every REA command has a class from REA's pinned tool-effect table: automatic ones run with `--rea`; approved ones (native binaries through Ghidra, IDA or Hopper, firmware regions through Binwalk on Linux, Electron JavaScript analysis, WebMCP discovery with `--webmcp` in a browser you opened on this computer) need `--onayla`, an isolation declaration (`--yalitim`) and `evet` in a terminal; dynamic ones (process observation of an ELF file, not on Windows) also need `--calistir` and `--sahibiyim`. `sezgi kesfet --yetenekler` lists them. Commercial engine output never leaves the local evidence store. Output: `kaynaksiz.json` plus the evidence store, graph, map and card (signable with `--imzala`), so MCP, the switchboard and `dogrula` work for it; facts at most `observed`, the preview never passes and every write needs approval.
- **Evidence and graph:** every claim is kept with its evidence (source kind, file and line, file digest, confidence on one scale `certain` > `observed` > `inferred` > `unknown`, completeness). Source kinds have ceilings, weak evidence does not add up, contradictions lower a claim, changed files make it stale. `graf.json` is the same claims as nodes and edges: endpoints, tables and their columns (with real table and column names), input fields and their validation rules, roles, NestJS modules, FastAPI routers, Django URL configurations and DRF routers, and Flask blueprints with the environment conditions a route is registered under, screens, UI actions, client calls, journeys, events and jobs. Plain JSON files, no database.
- **What the app is for:** the README, the package manifest, the OpenAPI title, table, model, path, module and role names are counted against a dictionary of about twenty-five business domains, the app's own description weighing more than table names and table names more than paths; a domain is named only with two kinds of evidence and a clear lead (more when the evidence is only code names, never against a description naming another domain), otherwise it is `unknown` with the candidates. Project templates and example apps are told apart from their domain. Why the app exists is its own sentence, quoted with file and line; the problem it solves is the domain's description (only for a known domain) plus a quoted benefit sentence from the README's descriptive part, never from a security or setup section. Users are grouped into types (anonymous, signed-in, API key / token client, administrator, role names) with sign-up, login, password-reset, SSO, e-mail and 2FA flows; operations into business capabilities (`cap:` nodes such as `cap:album.share`, which their endpoints `IMPLEMENTS`). Everything is at most `inferred`. `kimsin`, `rapor`, Ayna's **Ne biliyoruz** questions 1–5 and 17, and the card (`app.x-meaning`, `app.description`) show it.
- **Staying current:** `sezgi izle` (`watch`) re-parses only files whose content changed and rewrites the map atomically; a running MCP server reloads it. Staleness everywhere (watch, the write gate, `doktor`, `paylas`) is decided by file content, not timestamps.

- **Call graph and deep service analysis:** a function call graph over TypeScript / JavaScript, Python, Java, Kotlin, C#, Go, PHP and Ruby, stored as `CALLS` edges with file and line. A static, single target (same class, import, injected service of known type, ASP.NET Core registration in code, FastAPI `Depends(Class)`, Rails `before_action`) is `certain`; the only implementation of an interface, the Laravel container, MediatR and name matches are `inferred`; dynamic calls get no edge and are counted as unknown. From each endpoint down to the service and repository layers: table effects (Kysely, Prisma, TypeORM, Sequelize, Mongoose, SQLAlchemy / SQLModel, Django ORM, Spring Data JPA, EF Core, GORM, Eloquent, ActiveRecord, MyBatis XML mappers, raw SQL), access checks (`requireAccess`, `authorize`, `@PreAuthorize`, policies) as object-level authorization claims, and ownership comparisons. Kysely table classes (`@Table({ name })`) become table nodes. The card's `x-dna` carries `auth.object_level` (access checks and ownership with stamps and sources) and `call_chain`. Shown in `tani` (call chain), `etki`, the preview (object-level checks cannot be checked, so the write waits for approval), `rapor` and Ayna's questions on function calls, tables and authorization. On Immich, 251 of 295 operations are now linked to tables (none before) and 121 have an object-level access check.
- **External effects, reversibility and preconditions:** outgoing HTTP clients, queue and event publishing, e-mail, payment and cloud SDKs are found in seven languages and tied to operations through the call chain, also over the function call graph: polymorphic dispatch (same-named methods of subclasses, or of the project when the receiver's type is unknown; at most `inferred`) and the package a library call enters, import aliases included, classified as outgoing, internal or unclassified (healthchecks: test notifications, sign-in e-mails and S3 uploads were missed before, 34 operations reach outside now); the target is `certain` for a fixed address, `inferred` from an environment variable, `unknown` when not resolved (graph node `external:<host | ortam.NAME | sdk>`, card `x-dna.side_effects` and `x-external`). Every write gets a reversibility verdict (yes / partly / no / unknown) with its reason from soft deletes (also model-level and inherited), restore endpoints, reverse actions (`flag` / `unflag`, `unvote`, a DELETE on the same path after an add or a mark, `/cancel`, `/undo`, `/geri-al`; an update is never undone by a delete, and a collection-wide DELETE is not the reverse of creating one record: on Immich wrong reverse operations went from 15 of 24 to 0), version and history records on updates (revision tables, PaperTrail, Audited, Envers, django-simple-history, django-reversion, Laravel revisions, EF Core temporal tables) with a revert endpoint of the same resource, hard deletes, cascades, transaction boundaries and external effects, at most `inferred`. Relative calls of DI-registered clients take the registered base address (ASP.NET `AddHttpClient<T>(o => o.BaseAddress = ...)`, NestJS `HttpModule.register({ baseURL })`, Spring `WebClient` / `RestClient` builder beans). Conditional rejections in the chain become preconditions, including ones without a status code; the preview does not say PASS for them. `tani`, `etki`, `rapor`, Ayna questions 10, 12 and 13 and `santral baglar` (a call to another member's base is a cross-application link) show it.
- **Ownership rule corrected:** only a comparison of the record's owner field with the requester's identity is an ownership check; a 409 uniqueness check (`existing.id != user_id`) and "you cannot delete your own account" (`auth.user.id === id`) no longer count, nor does a filter by a path parameter (`delete(Item).where(Item.owner_id == user_id)`).
- **Preconditions follow the real chain:** `self.save()` resolves only to the object's own class, never to a same-named function in another file; Django error responses (`return HttpResponseForbidden()`, `JsonResponse(..., status=400)`) are rejections (healthchecks: login and pause no longer carry another view's 403; the API pause shows its own).
- **Unreadable route sources are reported:** a place where the code registers routes that Sezgi cannot read (a router mounted in the app whose routes cannot be read, an unrecognised route decorator, a path built at run time, plus the dynamic and unresolved registrations other adapters already listed) is counted for every adapter; `init`, `rapor`, `doktor`, Ayna's coverage card and its "What can it do?" answer and the Benlik Card (`x-unread_route_sources`) say "unreadable route source: N places (file:line)" and call the coverage partial, not complete.
- **FastAPI class-based views:** methods of a class decorated with `@controller(router)` / fastapi-utils `@cbv(router)` are read as endpoints with the router's prefix; the class's `Depends(...)` attributes, inherited ones included, are dependencies of each endpoint (Mealie: 28 → 289 operations).
- **Access checks are stricter:** OAuth and identity-provider client calls (`authorize_access_token`, `authorize_redirect`, `Socialite::driver()->user()`, `passport.authenticate`) and ORM relations (`belongsTo`, `belongsToMany`) are not access checks; `certain` is given only to a framework authorization API (`$this->authorize`, `Gate::allows`, `$user->can`, `can?`, `AuthorizeAsync`, `has_object_permission`), a check named by the project (`requireAccess`) is at most `inferred`. A call without a receiver in PHP, Python, JavaScript / TypeScript and Go never resolves to a class method: Laravel's global `redirect()` is no longer linked to a same-named controller method, whose 403 was attributed to other operations.
- **Permanent deletes are irreversible whatever the method:** a write that permanently deletes records (`POST /trash/clear`, a purge, `forceDelete`, or a bulk query delete: Eloquent `Model::where(...)->delete()`, Django `.filter(...).delete()`, SQLAlchemy `query(...).delete()` / `delete(Model).where(...)`, TypeORM `createQueryBuilder().delete()`, ActiveRecord `where(...).delete_all`, EF Core `ExecuteDelete`, also when the chain spans several lines) is "no", not "partly", and waits for human approval because it cannot be undone, independent of external effects. A write that changes credentials (a password, token, API key, secret or two-factor setting, named by its path or function) also waits for approval when its reversibility is not shown. On a soft-deleting model (`SoftDeletes`, paranoid, `deletedAt`) a plain `delete()` is not permanent; `forceDelete` is.
- **No false contradictions:** only evidence of another source kind (code, capture, database schema, human confirmation) can contradict a claim; different values from the same kind (one input name required in one operation and optional in another, two migrations of one table) depend on the context and are noted, not counted. Pydantic and SQLModel classes without `table=True` are not tables, and one validation line shared by several DTOs is one rule. Contradicted claims on clean repositories went to 0 (fastapi-template 21, Immich 27, BookStack 18, proshop 3); a capture that disagrees with the code still counts, with the same number in `rapor`, Ayna and MCP. `etki` reports a table as written when the operation both reads and writes it. Exposed and SQLAlchemy joins read the joined table.

### Run-time observation
- `sezgi gozlem al <file.har>` (`observe import`): imports a browser network capture. Only the shape of each request is kept (method, path template, status code, field names and JSON types, query parameter names); no body or query values, headers, cookies, tokens or e-mail addresses, and only the HAR file's digest. A matching request is evidence that the endpoint works, which errors it returns and what it answers (at most observed); a request or response that disagrees with the code's schemas is a contradiction; an observed endpoint the code does not have is reported as unknown. `--isaretler` links time marks to requests (inferred only).
- Every request live mode actually sends (`cagir`, operation tools, approvals, plan steps) is recorded the same way, without the human or the token.
- `sezgi gozlem senaryo <scenario.json>` (`observe scenario`): runs a browser scenario you wrote through REA in a browser you opened on this computer and links each UI step to the requests it started; UI steps and journeys become observed (inferred without isolation). It is in the dynamic class (`--onayla`, `--yalitim`, `--calistir`, `--sahibiyim` and `evet` in a terminal), works only on this computer (loopback), and the values it fills come only from environment variables or files, never from the scenario or the command line.
- Observations live in `.sezgi/gozlem.json`, rebuild the evidence store at once, enter the card on the next `init` and go stale when the endpoint's source file changes. `tani` shows them.

### Serving agents
- `sezgi mcp`: MCP server over stdio with `kimsin`, `ara`, `tani`, `onizle` (check a request against the rules without calling the app; rules it cannot check are listed, never guessed), `kanit` (claims and their evidence), `bilinmeyenler` (what the map does not know), `etki` (what a change can touch), `cagir` and `onay_durumu` (live mode). English names and texts with `--lang en` (or `SEZGI_LANG=en`, or an English system language): instructions, every tool answer, preview details and verdicts, behaviour summaries, reversibility reasons and evidence notes, meaning summaries, task plans and error texts; data taken from the code stays as it is. Code-derived text is reduced to plain text, length-limited and marked as data.
- **Turkish and English search:** `ara` (`search`) and Ayna's search box translate a request such as "kullanıcı sil", "fotoğraf yükle" or "delete user" into the code's words and the HTTP method of the verb (dictionary, Turkish suffixes, English plurals); a request naming something the app has no endpoint for finds nothing instead of a verb-only match. With `gorev: true` (`task: true`) a natural-language task ("kullanıcıyı sil ve albümlerini başkasına devret") becomes ordered steps, each with its endpoint, login, roles or permissions and whether it waits for approval; each step pairs its verb with its object (a read verb never picks a write, an operation whose action does not fit the verb is not picked, a step without an object takes the fitting one from the step before); reads come first and deletes last, a missing step is said to be missing, and nothing runs.
- **Operation tools:** with a token, each operation the token allows becomes its own MCP tool (name from the operation, description from the code, input schema from the map, read-only / destructive hints); above 40 operations (`SEZGI_ISLEM_ESIGI`) the search tools are used instead. An agent sees only what its token allows.
- `sezgi bagla` (`connect`): opt-in connection to the AI tools found on the computer (Claude Code, Cursor, VS Code, Gemini CLI, Codex, Claude Desktop, Windsurf), asked tool by tool, backed up; `--elle` prints the lines instead; when Sezgi runs from npm (`npx` or a project's `node_modules`) the connection is `npx -y sezgi@<version> mcp <map>` (`cmd /c npx …` on Windows) rather than a binary path that cleaning the cache would break, and `token olustur` and Ayna suggest the same command; `--yonlendir` adds an "ask Sezgi first" line to the tool's instruction file. `sezgi kaldir` (`remove`) undoes it byte for byte.
- `sezgi sun` (`serve`): HTTP + OpenAPI bridge on 127.0.0.1 for tools without MCP.
- `sezgi santral` (`switchboard`): several applications and clients behind one MCP server; `santral baglar` and the `baglar` tool find which client file calls which endpoint.
- **Entity mappings across apps:** `santral bagla-varlik` records that a field in one app is the same real-world thing as a field in another (schema level, no record values; a human definition is at most observed), source code that calls the other app with that field makes it certain, `santral varlik-gozle` compares values from both test copies in memory and keeps only counts and the match rate, and `santral varliklar` lists mappings and name / type suggestions (at most inferred). Over MCP, `varliklar` lists them and `etki` follows them into other apps (may affect, never certain).
- **Change plans:** the switchboard's MCP tool `plan` records one change across several apps and runs nothing. `sezgi plan listele | goster | onayla | reddet`: you see every step's app, operation, body, affected mapped entities and business rules, and approve steps in order with the content digest; each step passes the same gates as any live-mode write.
- `sezgi ayna` (`mirror`): local UI on 127.0.0.1 with the map, preview, coverage, card status and the permission screen that creates and revokes tokens; opens only with its keyed address (`--adres` prints it again). It opens on a **Sezgi** tab: a summary of what the app is (domain, the app's own sentence quoted with file and line, problem, user types, business capabilities; trust-stamped, at most inferred), a **Ne yapmak istiyorsun?** box (Turkish or English request → operations with what they write, external effects, reversibility and whether approval is needed; a plan for multi-step requests, never executed), and the four capabilities in order (understands the app, knows what each operation affects, explains it to the AI with evidence, lets the AI work safely), each with its real state and sub-states in this project (call graph present, external-call scan, MCP connections, card signature, live mode, human password), followed by look, several apps and without source code, and the next step. **Kapılar** shows for the selected operation, in plain words and stamped: what it does, who may do it (login, roles, object-level checks), the call chain, table effects with cascades, external effects, rejecting conditions, reversibility and the reason approval is or is not needed (same rule as live mode). **Ne biliyoruz** (what we know): all 17 founding questions in their original order and one style, answered only from the map, evidence store and coverage report with the counts `rapor` prints, each item trust-stamped, unanswerable questions shown as unknown with the reason and a helpful command. Without a map it opens with the introduction and `sezgi init`, writes nothing and loads the map once it appears. Keyboard tab navigation, light and dark themes, narrow screens (tabs wrap; summary counters stay off the introduction). Turkish and English: Ayna starts in the output language, an **EN / TR** button switches the page, cards, questions, operation details and search results, the browser remembers the choice, and each request carries its own language (`?lang=en`).
- `sezgi rapor`, `sezgi doktor`, `sezgi olc` (local measurement against your own OpenAPI), `sezgi paylas` (a signed, compressed map the team can commit; used only with a pinned key and byte-identical sources).
- `sezgi karsilastir` (`diff`): added, removed and breaking changes between two cards with reasons (including an operation whose address or method changed); `--sert` for CI. A GitHub Action (`action.yml`, example `eylem/ornek-is-akisi.yml`) runs it on pull requests and comments the result.
- Output language: every command speaks Turkish or English. `--lang en|tr` on any command, otherwise `SEZGI_LANG`, otherwise the system language (Windows display language, or `LC_ALL` / `LC_MESSAGES` / `LANG`); Turkish when it cannot be told. Help, errors, prompts, `doktor`, `rapor`, `init`, live mode, the switchboard and inspection without source code are translated; JSON keys and the files `init` writes do not change with the language.
- Help: `sezgi` alone says where you are and what to do next, and suggests Ayna; `sezgi yardim` lists every command in six groups with Turkish and English names; an unknown command suggests the closest one. Exit codes: `1` a command that failed, `2` a wrong command line (missing or invalid argument, unknown flag) with the command's usage line.

### Benlik Card (Draft 0.1.1)
- Operations, inputs, rules, roles, identity model and data ledger, every fact stamped; signed with ML-DSA-65 (FIPS 204) over RFC 8785 canonical JSON (`sezgi anahtar olustur`, `init --imzala`), verifiable with independent libraries.
- Draft 0.1.1 members: validity period (`x-issued_at` / `x-expires_at`, `init --gecerlilik`, default 30 days), per-file basis digests (`x-basis`; staleness is computed), the operation set's revision, evidence digests with a Merkle root and the separate, separately signed evidence bundle (`benlik-evidence.json`), a behaviour summary per operation (`x-dna`, with indirect cascade writes in `data_effect.indirect` and two-way conditions in `branches`), the response schema per operation (`x-response`), user journeys (`x-journeys`), internal events and jobs (`x-nodes`, `x-relationships`) and, for a card written by `kesfet`, `x-sourceless`, `x-app_node`, `x-preview`, `x-capabilities`, `x-screens` and `x-webmcp`.
- A card without an end time, or one that cannot be read, counts as expired: live mode does not write on it.
- `changes` is computed from the operations themselves, also without commits or git.
- `sezgi dogrula` checks the signature and key trust (pinned / first seen / changed), the validity period, the evidence root, the bundle and its signature, and stale operations; a damaged bundle is summarized per reason with the first record ids and the count, and every stale operation is counted and named. `sezgi anahtar sabitle` (`key pin`) pins a key.
- Validators for the card are published separately as `benlik` (npm, PyPI, crates.io); they agree on the shared test vectors and verify signatures.

### Live mode
- Off by default (`gozlem`, observe). `sezgi canli kur` (`live setup`) sets the target, mode, human session and first token in order; `sezgi canli` shows the status.
- **Gates for every request:** mode, token permission, a declared test-copy target or a target opened for real data (remote targets must be `https://`), a fresh map, a valid card (not expired, with a readable end time), the preview, the human's own session (effective permission = the user's permission ∩ the token), duplicate protection and a log that must accept the request first.
- **Approval:** a write goes without a human only when it is not destructive, its evidence is certain and not contradicted by other evidence (for example a HAR capture), the preview checked every known rule, any required role is verified for the human and the token does not ask for approval of every write. Verified roles come from the human's own declaration (`oturum ac --rol`, counted only in a terminal; with a system anchor only when signed with the human password), a signature-verified OIDC claim or the app's own "current user" endpoint; an agent's role claim is never trusted. The human sees the body and its digest (`onay goster`) and approves that digest; everything is checked again at approval time; concurrent approvals send one request. A write that reaches an external system or cannot be undone (hard delete, deleting without a shown way back) always waits for approval, and so does a write whose external effect is unknown (an unclassified library call, a dynamic call or a cut chain in its call graph; fail-closed); the card's `requires_approval` and Ayna say the same.
- **Tokens:** closed by default, expiring, revocable, stored as a hash; a pattern that opens writes on everything needs explicit confirmation (`--tum-islemler`); a pattern that matches no operation of the map is reported with the closest one (`--kesin` makes it an error). Tokens can also be made in Ayna.
- **Human session:** pasted (without a terminal, read as one line from standard input), or from the app's identity provider with the OIDC device flow and optional token exchange (`--oidc`, `--hedef-kitle`), renewed within the session limit.
- **Human key (`sezgi insan`, `human`):** proof of a human on real data. An administrator sets a password only the human knows into a system anchor (`sudo sezgi insan kur --sistem`; on Windows in an administrator terminal): PBKDF2-HMAC-SHA256 (600,000 rounds) into an Ed25519 key, of which only the salt and the public key are written, to a root-owned `/etc/sezgi/insan-<uid>.json` or an Administrators-owned `ProgramData\sezgi\insan-<user>.json` that the user cannot change. On Windows the setup takes the folder over if needed, cuts inheritance and writes an explicit access list (Administrators and SYSTEM full control, Users read only) on the folder and the file, and the anchor check reads the owner and the access list of both. `--kullanici` takes a uid or, on Linux and macOS, a user name. Opening real data, real-data tokens, every real-data approval and changing the hourly limit ask for the password in the terminal; the target record and real-data tokens are signed with it and checked before every write, so an edited `ayar.json` or `tokenler.json` closes writes (fail-closed). With an anchor, test-copy declarations and roles are signed too. An agent with shell access under the same account can open a pseudo-terminal and edit Sezgi's files, but without the password it cannot open, approve or re-sign; the password does not stop a program that learns it, runs as administrator or calls the app directly with the stored session (SECURITY.md, *Threat model*).
- **Writes on real data (experimental):** need the system anchor; opened only in a terminal (`hedef <url> --gercek-veri`, the human types the app's name and the human password; refused without a terminal or an anchor); only tokens made in a terminal with `token olustur --gercek-veri` and the password may write, older tokens only read; no automatic writes: every write waits for approval, given only in a terminal ("evet", or method and path for a destructive request, then the password; `--ozet` refused); a signed card containing the operation, a fresh map and a preview that checked every known rule are required before queueing and again at approval; at most 20 real-data writes per hour (`--saatlik-yazma`, terminal only); logged with `gercek_veri: true` and marked `GERÇEK VERİ` in MCP answers, `onay goster`, `hedef`, `canli` and `doktor`; an address once opened for real data is remembered (the same server written differently counts as the same address) and can be declared a test copy again only in a terminal, and a request queued on real data keeps those rules at approval; the approval text shows whether the operation looks reversible (Sezgi takes no backup). Change plans follow the same rules. A pseudo-terminal alone no longer opens anything there: the password is checked against the anchor; Sezgi still warns when it sees a pseudo-terminal or a known coding agent among its parent processes or in the environment.
- **Log:** hash-chained, without parameter values, encrypted at rest; `sezgi kayit --dogrula`, `--json` for an auditor.
- **Experience memory** (`sezgi hafiza ac`, off by default): an answered side-effect-free read is served from memory; never writes, never responses with e-mail addresses, session answers only with `--oturumlu`.

### Security model
- **Untrusted repositories:** symlinked files are not read, large files are skipped and reported, discovery stays inside the git root, output is never written through symlinks, malformed input never crashes the parser; files read without source code are bounds-checked and never executed.
- **Untrusted text:** code-derived text is stripped of control and invisible characters, length-limited and marked as data for the agent.
- **Local servers** (Ayna, `sun`): 127.0.0.1 only, Host and Origin checks, a per-launch key for Ayna, CSP without inline scripts, map values rendered as text only, request size and time limits, no CORS.
- **Writes:** only through the app's own public endpoints with the human's own session, only to a declared test copy or, with the stricter real-data gates, to real data a human opened in a terminal, never on a stale map or an expired card, never on an agent's claim of a role; live-mode state lives in the user's config folder with owner-only permissions and a cross-process lock.
- **Secrets at rest:** signing keys owner-only; the human session and the log key in the OS keychain on Windows and macOS, in an owner-only file on Linux; the log, request bodies waiting for approval and memory answers encrypted (ChaCha20-Poly1305).
- **Signatures:** separate contexts for cards, evidence bundles and share files, so one can never pass as another; a key next to a card proves integrity, not identity, so trust needs a pinned key.
- **External tools and browsers:** REA runs only as a pinned child process, without a shell, with time and memory limits; commands that start processes, write files or reach a browser need a human's approval in a terminal and an isolation declaration, and commands that run the target also need `--calistir` and `--sahibiyim`. Browser addresses (CDP, scenario start and navigation) must be on this computer. Raw REA output is deleted after reading; only names, signatures, counts and request shapes are kept, never page texts, string contents, decompiled code, request values, headers or cookies. Values a scenario fills reach REA only through its process environment.
- **Supply chain:** pinned toolchain, actions pinned by commit, `cargo-deny` and `cargo-audit` in CI, release builds without identity tokens and build provenance attested in a separate job.
- **Map bound to the card:** the card carries `x-map_digest`, the canonical SHA-256 of the map written with it. Live mode reads its approval decisions (`etki_onayi`, `dis_etki`, rules, stamps) from the map, so a write and an approval go through only if the map on disk matches the card and the operation in memory matches the map on disk; with a signed card the signature and the key's trust are checked too, and once a key has been pinned or seen for the application an unsigned card is refused. With an unsigned card the binding is a consistency check only.
- **Real data needs a pinned key:** a card signed by a key that is merely consistent with the one seen before no longer allows writes to real data; the key must be pinned with `sezgi anahtar sabitle`.
- **Sealed log:** every log line, the starting point after retention pruning and the last line are sealed with HMAC-SHA256 under the log key; `sezgi kayit --dogrula` detects a re-chained line, lines cut from either end and a hand-written starting point. `SEZGI_KAYIT_SIFRELEME=kapali` is ignored on real data.
- **Application responses are data:** responses forwarded to the agent are cleaned of invisible characters and labelled as data; the MCP instructions say so.
- **`SEZGI_IKILI` warning:** the npm launcher warns on stderr on every run when it starts a binary other than the package's own. SECURITY.md lists every environment variable Sezgi reads and what it changes.
- **REA outside Sezgi's folder:** when REA is found through `SEZGI_REA` or `PATH` instead of the folder `sezgi rea kur` installed, Sezgi says on stderr that its file contents are not verified.
- **Deeply nested calls no longer stall mapping:** the call graph asked tree-sitter for each call's parent and read each argument's whole text, both proportional to the nesting depth; a file with 50,000 nested calls took minutes. The walk now carries the parent and reads only the start of long arguments (the same file maps in about a second).

### Data and privacy
- `sezgi defter` (`ledger`) shows what Sezgi keeps; the log is kept 30 days by default (`--saklama 7..365`) and deleted when the period ends. `sezgi unut --kisi <id>` (`forget`) answers a KVKK / GDPR deletion request without breaking the chain; `--hepsi` removes all customer data. The card's `data_ledger` states this.
- `sezgi teshis` (`diagnostics`): optional local counters only, never sent.
- Observations (`gozlem.json`), entity mappings (`santral-varliklar.json`) and their observed matches keep shapes, counts and rates only, never record values. Change plans (`santral-planlar/`) are owner-only, with step bodies and arguments encrypted; the switchboard's other files (`santral.json`, `santral-baglar.json`, `santral-varliklar.json`) are owner-only too.

### Packages
- Documentation: the READMEs are a short guide (what Sezgi does, three-step start, safety, commands); everything else is in the detailed reference, `docs/REFERENCE.md` (English) and `docs/BASVURU.md` (Turkish).
- `npm install -g sezgi` / `npx sezgi` (Node.js 20+): a launcher that installs the prebuilt binary for Windows x64, macOS arm64 / x64 (macOS 11+) or Linux x64 / arm64 (glibc 2.34+).
- GitHub release workflow: Windows, Linux and macOS binaries with SHA-256 sums and build provenance, as a draft; publishing is a human decision. macOS binaries are built on native arm64 and x86_64 runners with a minimum of macOS 11.0, checked from the Mach-O header before packaging; the human session and the log key live in the Keychain.

### Known limitations
- Guards are recognized by name; a misleadingly named guard can give a wrong decision with a certain stamp. Conditionally applied decorators are not followed (inferred).
- Path prefixes from `enableVersioning` (URI), `RouterModule` and `setGlobalPrefix(..., { exclude })` are not applied.
- The call graph is static: run-time dependency bindings, dynamic dispatch and calls inside libraries are not followed; chains stop after 8 steps or 400 functions (marked partial); an interface is followed only to a registered class (certain) or its only implementation (inferred). Table links are always inferred.
- Rails: paths whose parameter is inside a segment (`/~:username`, `/c/:id.json`) keep the segment as written; mounted engines, `direct` / `resolve` and routes added by gems other than Devise are not read; filter blocks and lambdas passed as `if:` are treated as conditional.
- Front-end links read React, Next.js, Preact, Vue, Svelte, Angular, Remix / React Router v7 and Solid only; a screen's login requirement from a guard is inferred from its name and source; a `"use server"` function is followed into its calls but is not an endpoint itself; screen changes and journeys from code are always inferred.
- What an app is for comes from a dictionary of about twenty-five domains and from names: an app outside it, or with too little evidence, is `unknown`; capability names follow paths and function names (`inferred`).
- The behaviour summary reads recognized patterns and its coverage is always open: a rejection that is not listed may still exist. Cascades come from schemas and migration files (inferred).
- Observations keep shapes only, so they cannot tell which values a rule accepted; a HAR file carries no UI steps. Observations cannot be added to a map built by `kesfet`.
- Without source code, behaviour is read only through REA; process observation is not supported on Windows and firmware regions only on Linux.
- Writes on real data are experimental: they need an administrator-made system anchor and every step there is confirmed in a terminal with the human password, which an agent with shell access under the same user account does not know; it does not stop a program that learns the password, runs as administrator, replays an older signed record or calls the app directly with the stored session; Sezgi has not had an independent security audit yet.
